这些材料最容易踩的坑，是把“读完很多论文”当成目标。

更合适的姿势是：

> **带着问题读，围绕同一条问题链反复交叉阅读。**

对你现在这套材料，我建议用一个固定的 **6 步论文阅读法**。

1. **先问：这篇论文到底在解决什么问题？**  
    不要先看算法。先写一句话：
    
    - 系统原来哪里不行？
    - workload 是什么？
    - failure model 是什么？
    - 作者最想优化什么？
    
    比如 Dynamo：
    
    > “在节点故障和网络分区下，如何优先保证 key-value 服务持续可写？”
    
    Spanner：
    
    > “如何让跨地域数据库同时支持同步复制、事务和接近外部一致性的语义？”
    
2. **找 naive solution，并问为什么不工作。**  
    这一点特别重要，因为很多论文的价值就在于“为什么直觉方案不够”。
    
    例如：
    
    ```
    Dynamo
    naive: 单 leader + 强一致复制
    问题: partition 时 availability 下降
    
    Aurora
    naive: MySQL + EBS replication
    问题: write amplification + network IO 太高
    
    Frangipani
    naive: 每台 file server 自己缓存共享数据
    问题: cache coherence
    ```
    
3. **只抓一个核心 abstraction。**  
    第一遍读完，不要求记住所有细节，只要求回答：
    
    > 这篇论文最核心的新 abstraction 是什么？
    
    例如：
    
    |论文|核心 abstraction|
    |---|---|
    |Raft|replicated log|
    |Dynamo|quorum + version reconciliation|
    |Spanner|TrueTime interval|
    |Spark|RDD + lineage|
    |Frangipani|distributed lock + shared storage|
    |Aurora|log-is-the-database|
    |COPS|explicit dependency tracking|
    |CRDT|mergeable state/operation|
    
4. **手工跑一个最小例子。**  
    这是从“看懂”变成“真正理解”的关键。
    
    比如读 quorum，就自己画：
    
    ```
    N = 5
    W = 3
    R = 3
    
    Write quorum:
    A B C
    
    Read quorum:
        C D E
    
    intersection = C
    ```
    
    读 Raft：
    
    ```
    leader log:
    [1:a] [1:b] [2:c]
    
    follower A:
    [1:a] [1:b]
    
    follower B:
    [1:a] [1:x]
    ```
    
    然后问：
    
    - leader 怎么修？
    - crash 在这一步怎么办？
    - 哪个 invariant 保证安全？
5. **明确 correctness，不要只看 mechanism。**  
    每篇论文至少问四件事：
    
    ```
    Safety:
    什么事情绝不能发生？
    
    Liveness:
    什么事情最终必须发生？
    
    Failure Model:
    假设哪些故障可能发生？
    
    Invariant:
    哪条性质始终成立？
    ```
    
    例如 Raft：
    
    ```
    Safety:
    committed entry 不能被不同 command 覆盖
    
    Liveness:
    网络恢复且多数节点可用后，可以继续提交
    
    Failure model:
    crash-stop + message delay/loss/reorder
    
    invariant:
    leader completeness
    log matching
    ```
    
    这也是你最近问的 proof intuition 真正应该落地的地方。
    
6. **最后再问 trade-off。**  
    不要记“论文很好”，而是记：
    
    ```
    它获得了什么？
    ↓
    为此牺牲了什么？
    ```
    
    例如：
    
    ```
    Dynamo
    + availability
    + partition tolerance
    - stronger consistency
    - conflict resolution complexity
    
    Spanner
    + strong semantics
    + geo replication
    - coordination latency
    - clock infrastructure complexity
    
    LSM
    + sequential writes
    - compaction
    - read amplification
    ```

## 我建议你每篇论文只做一页笔记

不要抄论文。

固定用这个模板：

```
# Paper

## 1. Problem
它解决什么问题？

## 2. Why hard
为什么难？

## 3. Naive solution
直觉方案是什么？
为什么失败？

## 4. Core abstraction
最关键的新东西是什么？

## 5. Mechanism
核心流程怎么跑？

## 6. Correctness
- Safety
- Liveness
- Invariant
- Failure model

## 7. Trade-offs
得到什么？
牺牲什么？

## 8. Minimal example
自己跑一个小例子

## 9. Relation
和哪些系统/论文有关系？

## 10. One-sentence takeaway
一句话总结
```

# 不要按照“论文列表”读，要按照“问题链”读

这是最重要的建议。

比如你要学 **replication**，不要今天 Dynamo、明天 Spark、后天 B-Tree。

应该连续读：

```
Primary-backup
      ↓
Quorum
      ↓
Dynamo
      ↓
Vector Clock
      ↓
Causal Consistency
      ↓
COPS
      ↓
CRDT
```

这样每篇论文都在回答上一篇留下的问题。

同样，consensus 可以这样：

```
为什么需要 consensus？
      ↓
FLP
      ↓
Paxos
      ↓
Raft
      ↓
ZooKeeper
      ↓
etcd
      ↓
Spanner
```

Storage：

```
B-Tree
  ↓
Log Structured FS
  ↓
LSM Tree
  ↓
Bigtable
  ↓
LevelDB / RocksDB
  ↓
WiscKey / Titan
```

Transactions：

```

 ↓
MVCC
 ↓
Snapshot Isolation
 ↓

 ↓
SSI
 ↓
2PC
 ↓

```

这比“Top 60 从第一篇刷到第六十篇”有效得多。

# 三遍阅读法也很好用

### 第一遍：10~20 分钟

只看：

- Abstract
- Introduction
- Architecture figure
- Conclusion

目标只有：

> 我知道它解决什么问题，以及核心 idea 是什么。

如果第一遍还回答不出来，就不要钻算法细节。

### 第二遍：30~60 分钟

重点看：

- design
- protocol
- examples
- figures
- failure handling

开始手动画执行过程。

### 第三遍：真正精读

只针对值得精读的论文，例如：

- Lamport
- Raft
- Dynamo
- Spanner
- Aurora
- Frangipani
- LSM
- Bigtable

此时再看：

- proof
- corner cases
- evaluation
- implementation detail

**不是所有论文都值得第三遍。**

# 对你尤其适合的一种方式：Paper → Lecture → Implementation

你现在手里刚好有：

- DDIA
- MIT 6.824
- CMU 15-445
- BusTub / RocksDB 等代码

所以可以形成：

```
        Paper
          ↓
      理解 idea
          ↓
       Lecture
          ↓
     建立 mental model
          ↓
        Code
          ↓
     验证 implementation
```

例如：

```
LSM paper
   ↓
DDIA Storage Engine
   ↓
CMU 15-445 storage lectures
   ↓
LevelDB / RocksDB source
```

或者：

```
Raft paper
   ↓
MIT 6.824 lecture
   ↓
6.824 Raft lab
   ↓
etcd/raft
```

或者：

```
Spanner paper
   ↓
6.824 Spanner
   ↓
DDIA Transactions
   ↓
CockroachDB architecture
```

这个闭环的学习效果比纯读论文强很多。

# 读论文时最值得反复问的 10 个问题

你甚至可以把下面这 10 个问题固定贴在 Obsidian：

```
1. What problem?
2. Why is it hard?
3. What is the naive solution?
4. Why doesn't it work?
5. What is the core abstraction?
6. How does the protocol run?
7. What is the invariant?
8. Under what failure model is it correct?
9. What does it trade away?
10. What later systems reused this idea?
```

如果一篇论文你能独立回答这十个问题，我会认为你已经真正掌握它了。

---

最后，我会把你的学习重点从“我今天读了几篇”改成：

> **我今天真正搞清楚了哪一个系统问题。**

比如一天只搞清楚：

> 为什么 `R + W > N` 只说明 quorum overlap，却不能自动推出 linearizability？

这种收获，往往比泛读五篇论文更有价值。
