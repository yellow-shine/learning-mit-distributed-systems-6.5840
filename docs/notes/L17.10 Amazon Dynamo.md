# MIT 6.824 LEC 17 — Amazon DynamoDB

先给你这节课最重要的定位：

> **DynamoDB 这节课真正想教的，不是“怎么做一个 distributed key-value store”，而是：当一个 distributed database 变成超大规模、multi-tenant、fully managed cloud service 后，怎样让每个客户仍然获得像“独占数据库”一样可预测的性能、可用性和 durability。**

这和前面 Raft / Spanner 的味道很不一样。

Raft 更多是在问：

> “多个 replica 怎么对同一个状态达成一致？”

DynamoDB 这节课进一步问：

> **“即使 replication 已经做对了，为什么一个拥有几十万客户、无数 partition、海量请求的真实数据库仍然会挂？”**

MIT 使用的材料是 2022 USENIX ATC 论文 **Amazon DynamoDB: A Scalable, Predictably Performant, and Fully Managed NoSQL Database Service**，课程 slides 把主题总结为 Availability、Consistency、Predictability、Scalability。[MIT CSAIL PDOS](https://pdos.csail.mit.edu/6.824/notes/DynamoDB-MIT-Lecture-2023.pdf?utm_source=chatgpt.com)

---

# Part 1：如果只允许记住一个问题

## 这个问题是

> **怎样在一个共享基础设施的 distributed database 中，让任意规模、任意流量模式的客户都获得 predictable performance，同时一个 partition、一个 server、一个 AZ 或另一个 customer 出问题时，不把整个服务拖垮？**

假设最开始只有一个用户：

```
Client
  |
  v
Database Server
```

只要机器还有 CPU、memory、disk，你基本知道：

```
100 requests/s -> OK
500 requests/s -> maybe OK
10000 requests/s -> overloaded
```

容量模型虽然简单粗暴，但比较容易理解。

现在变成：

```
             DynamoDB

 Customer A ----\
 Customer B -----+---- Request Routers
 Customer C ----/           |
                             v
                    +----------------+
                    | Storage Nodes  |
                    | A B C D E ...  |
                    +----------------+
```

Customer A 可能突然从：

```
100 req/s
```

跳到：

```
1,000,000 req/s
```

而 Customer B 希望：

```
"My latency should not change."
```

这就是 multi-tenancy 的核心麻烦。

更麻烦的是，即使一个 table 总共有足够 capacity，也可能产生：

```
Partition 1    Partition 2    Partition 3
 capacity=100  capacity=100    capacity=100

     ↓
     ↓ 250 requests/s
     ↓

traffic = 250       10             10
```

总流量：

```
270 < 300
```

理论上整个 table 有足够能力。

但如果 capacity 被死板地切成：

```
100 + 100 + 100
```

Partition 1 仍然会 throttle。

于是出现一个很反直觉的问题：

> **整个 database 明明还有大量空闲 capacity，一个 hot partition 却已经不可用了。**

这正是 DynamoDB 多年演进中反复处理的问题之一。Lecture 从 per-partition provisioning 逐渐引出 global admission control、bursting、adaptive capacity / repartitioning 等机制。[MIT CSAIL PDOS](https://pdos.csail.mit.edu/6.824/notes/DynamoDB-MIT-Lecture-2023.pdf)

你可以把课程进展理解成：

## Raft vs DynamoDB

Raft解决：

```
Leader election
Log agreement
Replica consistency
Crash fault tolerance
```

核心问题：

> 一组 replicas 怎样安全地产生一个共同 log？

DynamoDB的问题更大：

```
replication
+
partitioning
+
routing
+
multi-tenancy
+
capacity isolation
+
hot partitions
+
deployment
+
metadata
+
durability verification
+
transactions
```

所以：

> **Raft 是一个 replication / consensus protocol。  
> DynamoDB 是整个 database service。**

你不能拿 Raft 和 DynamoDB 做同层比较。

---

## Spanner vs DynamoDB

Spanner的核心目标之一是：

```
global distribution
+
strong consistency
+
distributed transactions
```

它愿意为强语义建立复杂机制，例如 TrueTime。

DynamoDB 最初选择的是不同路线：

```
simple KV API
+
horizontal partitioning
+
predictable latency
+
massive scale
```

后来再逐渐增加：

```
strongly consistent reads
transactions
global tables
secondary indexes
```

Lecture slides 明确区分 single-region replica group 和 Global Tables：region 内可以提供 strongly consistent reads，而经典的跨 Region Global Tables 路径强调 asynchronous replication / eventual convergence，并涉及 conflict resolution。[MIT CSAIL PDOS](https://pdos.csail.mit.edu/6.824/notes/DynamoDB-MIT-Lecture-2023.pdf)

---

## Dynamo vs DynamoDB

这是本课第一个必须纠正的 mental model。

### 2007 Dynamo

经典论文：

> Dynamo: Amazon's Highly Available Key-value Store

强调：

```
always writable
eventual consistency
consistent hashing
sloppy quorum
vector clocks
hinted handoff
application conflict resolution
```

为了 availability，可以牺牲 consistency。[Amazon Science](https://www.amazon.science/publications/dynamo-amazons-highly-available-key-value-store?utm_source=chatgpt.com)

### DynamoDB

不是“Dynamo 加了 DB”。

它已经演化成完全不同的 managed database architecture：

```
Request Router
      |
      v
Partition Metadata
      |
      v
Storage replicas
```

包括 partition management、capacity control、strong reads、transactions 等。

所以：

> ❌ DynamoDB = 2007 Dynamo 的云托管版

并不准确。

更好的理解是：

> **Dynamo 提供了 DynamoDB 的历史和设计思想起点，但 DynamoDB 是后来重新演化出来的 hyperscale managed database。**

# Part 3：六个核心 Mental Models

我建议这节课只牢牢记住六件事。

---

## 1. Logical Table ≠ Physical Partition

用户看到：

```
Users Table
```

实际上底层可能是：

```
Users

hash range 0x0000~0x3fff -> Partition P1
hash range 0x4000~0x8fff -> Partition P2
hash range 0x9000~0xffff -> Partition P3
```

DynamoDB 对 key 做 hashing，并把 hash space 拆成 physical partitions。Lecture slides 就是从 table → hash → partition 逐步展开的。[MIT CSAIL PDOS](https://pdos.csail.mit.edu/6.824/notes/DynamoDB-MIT-Lecture-2023.pdf)

### 为什么需要？

如果：

```
1 machine = 10 TB / 100k QPS
```

你的 table 需要：

```
100 TB / 1M QPS
```

就只能：

```
partition horizontally
```

于是扩容变成：

```
P1 P2 P3
     ↓ hot
split
     ↓
P1 P2a P2b P3
```

这就是 distributed database scalability 的基本来源。

### 误区

❌ Partition key value 就等于 physical partition。

不是。

同一个 physical partition 可以承载很多 partition-key values；随着实现和表结构不同，DynamoDB 还可能进一步调整数据的物理 placement。

---

## 2. Capacity isolation

这其实是 DynamoDB 最有意思的 cloud abstraction 之一。

想象：

```
Customer A
  buys 100 RCU

Customer B
  buys 10000 RCU
```

RCU/WCU 不只是 billing 概念。

它还是：

> **resource isolation abstraction**

早期可以近似理解为：

```
Token Bucket

capacity = 100

tokens
  ↓
100 / second

Get -> consume token
Get -> consume token
...
```

如果没 token：

```
throttle
```

Lecture slides 就用 token bucket 来解释 provisioned capacity。[MIT CSAIL PDOS](https://pdos.csail.mit.edu/6.824/notes/DynamoDB-MIT-Lecture-2023.pdf)

其目的不是单纯限流。

而是避免：

```
Customer A traffic spike
       ↓
storage node overloaded
       ↓
Customer B latency ↑
       ↓
Customer C timeout
```

也就是经典：

> **noisy neighbor problem**

---

## 3. Hot Partition

这是 partitioning 最重要的 failure mode。

你可能认为：

```
hash(key)
```

以后 traffic 自然均匀。

不一定。

例如：

```
key = celebrity_user_id
```

突然一个热门主播：

```
user=Taylor
```

占了整个 workload 的 80%。

即使：

```
Hash("Taylor") = random-looking number
```

它依然只落到某个 partition。

Hashing 只能帮助：

> key distribution

不能保证：

> request distribution

这两个一定要分开。

---

## 4. Adaptive Capacity / Split for Heat

naive solution：

```
Table capacity = 300

P1 = 100
P2 = 100
P3 = 100
```

结果：

```
P1 needs 250
P2 needs 10
P3 needs 10
```

P1 被 throttle。

这就是：

```
capacity exists
but cannot be used where needed
```

后来 DynamoDB 引入更 global 的 capacity decision，减少这种固定 partition allocation 带来的 throughput dilution，并通过 adaptive capacity / split-for-heat 适应长期热点。AWS 描述的 split-for-heat 会根据持续的热点把 physical partition 拆开，从而提供更多处理 capacity。[InfoQ](https://www.infoq.com/presentations/dynamodb-scale-aws/?utm_source=chatgpt.com)

Mental model 应该是：

```
Logical Capacity
       |
       v
Global Admission
       |
       v
Traffic-aware placement
       |
       v
Physical partitions
```

而不是：

```
每个 partition 永久固定 1/N capacity
```

---

## 5. Predictability > Absolute Efficiency

这是我认为整篇 2022 DynamoDB paper 最值得基础设施工程师记住的设计原则。

考虑 metadata cache：

```
Request Router
      |
   cache hit
      |
      v
metadata cached locally
```

99.75% cache hit rate，看起来非常优秀。

但意味着 backend metadata system 平时只承担：

```
0.25%
```

流量。

某次 cache 同时失效：

```
0.25%
 ↓
100%
```

backend 突然承受：

```
400x
```

load。

然后：

```
metadata overload
      ↓
routers cannot route
      ↓
more retry
      ↓
more load
      ↓
service collapse
```

这就是非常典型的 metastable / cascading failure。

DynamoDB 后来的设计哲学是：

> 不允许 cache 把真正的 backend work 完全隐藏掉。

它引入 MemDS 等机制，使 metadata path 能够持续承受可预测的负载，而不是平时几乎无流量、cache miss 时突然爆炸。Amazon 将这一经验总结成 **predictability over absolute efficiency**。[Amazon Science](https://www.amazon.science/blog/lessons-learned-from-10-years-of-dynamodb?utm_source=chatgpt.com)

这和你做 Kubernetes/control plane 很相关：

```
cache hit rate = 99.99%
```

并不自动等于：

```
architecture robust
```

真正的问题是：

> **cache 全 miss 时，你的系统还能不能活？**

---

## 6. Continuous Verification

Replication 并不等于 durability 已经解决。

三个 replica：

```
Replica A
Replica B
Replica C
```

你可能觉得：

```
3 copies
=> data safe
```

不一定。

因为可能存在：

```
software bug
bit rot
silent corruption
bad disk
bad memory
buggy replication
```

甚至：

```
A = corrupted
   ↓ replication
B = corrupted
C = corrupted
```

于是：

> replication 可以把错误复制得非常可靠。

DynamoDB 因此大量使用 checksums，并持续进行 data-at-rest verification；paper 描述 scrub 会比较 replicas，并将 live replica 与通过 archived WAL 重建的数据进行验证。[USENIX](https://www.usenix.org/system/files/atc22-elhemali.pdf?utm_source=chatgpt.com)

这个思想非常值得记住：

> **Replication answers “do I have copies?”  
> Verification answers “are those copies actually correct?”**

# Part 4：System Model

这里必须区分“论文公开了什么”和“我们推导什么”。

## Node Model

DynamoDB显然按现实 cloud 系统处理：

```
crash
restart
disk failure
AZ failure
software deployment failure
```

而不是：

```
crash-stop forever
```

所以总体更接近：

```
crash-recovery
```

并且 storage state 持久化。

它还显式考虑 silent corruption，但这不是 classical Byzantine protocol：

```
Byzantine node intentionally lies
```

并不是核心 adversary model。

---

# Network Model

必须能够处理：

```
packet loss
delay
reordering
timeout
partition
```

现实系统不存在可靠 latency upper bound。

因此从算法思维上，更接近：

```
asynchronous / partially synchronous practical system
```

你不能把 timeout 理解成：

```
timeout
=> machine dead
```

timeout 只能告诉你：

```
I don't know what happened.
```

和 Raft 完全一样。

---

# Storage Model

一个 logical partition 有多个 replicas，跨 Availability Zones。

Lecture 中简化为类似：

```
        Partition P

         Leader
         AZ-1
        /     \
       /       \
Follower       Follower
 AZ-2           AZ-3
```

slides 将 single-region replication 展示为跨三个 AZ，并在 consistency 部分标出 leader storage node；AWS 的工程资料也描述一个 partition 的数据跨三个节点保存。[MIT CSAIL PDOS](https://pdos.csail.mit.edu/6.824/notes/DynamoDB-MIT-Lecture-2023.pdf)

---

# 一个非常重要的知识边界

不要自行推出：

```
DynamoDB replication = Raft
```

公开论文谈到了 proprietary replication protocol，并指出核心 replication protocol 曾使用 TLA+ model checking，但这节课并没有把完整 replication protocol 展开成一个 Raft-like algorithm。[Xing Lin](https://xinglin.github.io/dynamodb/?utm_source=chatgpt.com)

所以最严谨的说法是：

```
Leader-based replicated partition
+
internally fault-tolerant replication protocol
```

而不是无依据地说：

```
它就是 Paxos
```

或者：

```
它就是 Raft
```

# Part 5：一次 Put 到底发生什么？

先忽略 failure。

假设：

```
Put(user123, {...})
```

大致 logical path：

```
Client
   |
   | Put(k,v)
   v
Request Router
   |
   | hash(k)
   | lookup partition metadata
   v
Partition P17
   |
   v
Leader Storage Node
   |
   +------ Replica AZ2
   |
   +------ Replica AZ3
```

Lecture 的 architecture 就由：

```
Authentication
Request Router
Metadata
Storage Nodes
```

这些部分组成。[MIT CSAIL PDOS](https://pdos.csail.mit.edu/6.824/notes/DynamoDB-MIT-Lecture-2023.pdf)

---

## Step 1：Authentication

先判断：

```
Who are you?
Can you Put this table?
```

---

## Step 2：Routing

Router 计算：

```
hash(partition_key)
```

假设：

```
hash(user123) = 0x8231
```

metadata：

```
0x0000 - 0x6fff -> P1
0x7000 - 0xbfff -> P2
0xc000 - 0xffff -> P3
```

于是：

```
0x8231 -> P2
```

---

## Step 3：Admission Control

检查这个 tenant / table 是否允许消耗 capacity。

例如：

```
token available?
```

没有：

```
Throttle
```

有：

```
continue
```

---

## Step 4：write 到 leader

```
Router
  |
  v
Leader(P2)
```

Leader负责协调 partition 内的数据更新。

---

## Step 5：Replication

logical view：

```
Leader
  |
  +----> Replica B
  |
  +----> Replica C
```

经过足够的 durable replication 之后，请求才可安全完成。

完整 acknowledgement protocol 属于内部 replication implementation，Lecture 并未公开到 Raft 那样的逐消息规格，因此不要自己补出来。

# Part 6：Read 为什么有 Strong / Eventual 两种？

Lecture slides 非常清楚地画了：

```
Get

Strongly consistent
vs
Eventually consistent
```

并以 leader + replicas 解释。[MIT CSAIL PDOS](https://pdos.csail.mit.edu/6.824/notes/DynamoDB-MIT-Lecture-2023.pdf)

假设：

```
Leader:   x=2
Replica1: x=2
Replica2: x=1
```

因为 Replica2 replication 落后。

### Strong Read

最简单 mental model：

```
read authoritative up-to-date path
```

例如 leader：

```
Client -> Leader -> x=2
```

这样 latency / available read capacity 受 leader path 约束。

### Eventually Consistent Read

可以：

```
Client -> any replica
```

可能看到：

```
x=1
```

但读扩展能力更强。

AWS 关于 physical partition 的公开工程说明也指出 strongly consistent reads 依赖 leader，而 eventually consistent read 可以利用多个 replicas，因此读 capacity 有不同特征。[Amazon Web Services, Inc.](https://aws.amazon.com/blogs/database/part-2-scaling-dynamodb-how-partitions-hot-keys-and-split-for-heat-impact-performance/?utm_source=chatgpt.com)

---

# Timeline

```
time →

Client A: Put(x=2) -------->

Leader:       x=2
              |
              +--------> Replica1 x=2
              |
              +----------------------> Replica2 x=2

Client B:
                   Get eventual
                        |
                        v
                    Replica2
                    returns x=1
```

这不是 storage corruption。

只是：

```
replication lag
```

# Part 7：Scalability

假设刚开始：

```
hash range

0x0000 -------------------- 0xffff
           P1
```

数据越来越多：

```
P1
```

变成：

```
P1a          P1b

0x0000----0x7fff
0x8000----0xffff
```

再增长：

```
P1 P2 P3 P4 P5 ...
```

于是整体 throughput：

```
capacity ≈ sum(partition capacities)
```

这是 horizontal scaling。

核心 invariant：

```
For every key hash h:
there should be a well-defined current owner partition.
```

否则：

```
Put goes P1
Get goes P2
```

你就直接丢 consistency 了。

因此 partition metadata 实际上也是非常重要的 distributed control-plane state。

---

# Part 8：最精彩的演进：Hot Partition

先从 naive design 开始。

Table：

```
300 RCU
```

3 partitions：

```
P1: 100
P2: 100
P3: 100
```

工作负载：

```
P1: 250
P2:  10
P3:  10
```

结果：

```
Table consumed = 270 < 300

BUT

P1 requested = 250 > 100

=> throttle
```

这就是一个非常漂亮的反例：

> **global capacity sufficient ≠ local capacity sufficient**

---

# Mechanism 1：Global Admission Control

把 decision 从：

```
per partition
```

提升到：

```
per table
```

概念上变成：

```
             300 RCU budget
                   |
             Global Control
              /    |    \
             /     |     \
           P1      P2     P3
          250      10     10
```

于是 capacity 可以更灵活地被实际 workload 使用。

MIT slides 专门从 non-uniform partition traffic 过渡到 Global Admission Control。[MIT CSAIL PDOS](https://pdos.csail.mit.edu/6.824/notes/DynamoDB-MIT-Lecture-2023.pdf)

---

# Mechanism 2：Bursting

假设平时：

```
provisioned = 100
usage = 20
```

没有使用的 capacity 某种程度上可以形成：

```
banked burst capacity
```

然后短时间：

```
300 req/s
```

不一定立即 throttle。

但 bursting 解决的是：

```
short spike
```

不是：

```
permanent hotspot
```

---

# Mechanism 3：Adaptive Capacity / Split for Heat

如果热点持续：

```
        P1
      5000 QPS
```

可以：

```
        P1
       /  \
     P1a  P1b
```

如果 traffic 可以被分开：

```
2500     2500
```

那么 physical throughput 增加。

这就是：

> **让 partitioning 根据 workload 变化，而不只是根据 data size 变化。**

这是 paper 一个非常现代的观点：

```
data placement
should follow
traffic distribution
```

而不仅仅是：

```
data distribution
```

---

# 一个关键 counterexample

如果：

```
key = "celebrity-user-1"
```

而所有请求都精确访问同一个 item：

```
Get("celebrity-user-1")
```

你把 keyspace split 成：

```
P1a P1b P1c P1d
```

也没用。

因为：

```
one item
```

不能同时 magically 变成 4 个独立 writable shards。

这就是：

> partition-level hotspot

和：

> single-key hotspot

必须区分。

# Part 9：Availability

Region 内：

```
             Partition P

 AZ1             AZ2              AZ3
  |               |                |
Replica A       Replica B        Replica C
```

这解决：

```
server failure
disk failure
AZ failure
```

而不是只做：

```
rack-level replication
```

DynamoDB paper/lecture 强调 multi-AZ replication；Global Tables 则进一步跨 Region。[MIT CSAIL PDOS](https://pdos.csail.mit.edu/6.824/notes/DynamoDB-MIT-Lecture-2023.pdf)

---

# Failure #1：一个 storage node crash

```
A down
B alive
C alive
```

系统可以继续通过剩余 replica group 运作，并修复 replica redundancy。

---

# Failure #2：整个 AZ down

```
AZ1 ❌

AZ2 ✅
AZ3 ✅
```

因为 replica 跨 AZ：

```
service can continue
```

这就是为什么：

```
3 copies in same rack
```

远远弱于：

```
3 copies across failure domains
```

---

# Failure #3：Region failure

single-region replication 不解决。

需要：

```
Global Tables
```

例如：

```
US-West
   |
   +------ Europe
   |
   +------ Asia
```

# Timestamp Ordering

这里和你学过的 CMU 15-445 Timestamp Ordering 可以直接接上。

每个 transaction 得到：

```text
timestamp T
````

例如：

```
T1 = 100
T2 = 120
T3 = 130
```

这建立一个 logical serial order：

```
T1 < T2 < T3
```

Storage node 判断：

> 当前这个 transaction 是否还能在它的 timestamp 位置合法执行？

如果不能：

```
abort
```

DynamoDB transactions paper 明确使用 timestamp ordering 来定义 serial order，并让 storage nodes 检查冲突。[USENIX](https://www.usenix.org/conference/atc23/presentation/idziorek?utm_source=chatgpt.com)

注意：

> Timestamp 并不是“记录一下时间”这么简单。

它真正承担的是：

```
serialization order
```

# Part 13：Safety vs Liveness

## Safety

Safety 问：

> **什么事情绝对不能发生？**

例如：

```
acknowledged write silently disappears
```

或者：

```
half transaction becomes permanently visible
```

或者：

```
strongly consistent read sees an impossible older state
```

或者：

```
two replicas永久 divergence 而系统认为都是正确的
```

---

# Liveness

Liveness 问：

> **正常条件恢复后，请求最终还能不能处理？**

例如：

```
one storage node dies
```

系统不应该永远停止。

或者：

```
partition becomes hot
```

系统应该 eventually adjust capacity / partition placement。

这里可以明显看到：

```
Safety
≠
Availability
≠
Predictable latency
```

一个系统完全可以：

```
100% correct
but
p99 = 5 minutes
```

从数据库理论上可能“安全”。

从 DynamoDB 产品角度已经失败。

这就是这节课和纯 consensus lecture 最大的差别之一。

# Part 14：Failure Matrix

|Failure|系统反应|Data safety|Availability|
|---|---|---|---|
|一个 replica crash|剩余 replicas 服务并修复 redundancy|应保持|通常保持|
|一个 AZ failure|其他 AZ replicas 接管|应保持|设计目标是保持|
|Request packet loss|timeout/retry|protocol 必须防止重复副作用|latency 可能增加|
|Metadata cache failure|fallback path|数据本身未必受损|可能引发严重 cascading failure|
|Hot partition|throttle / adaptive mechanisms / split|数据安全|局部 availability 下降|
|Region failure|single-region table 受影响；multi-region topology 可用于恢复|取决于 replication progress|Global Tables 提供更强 region resilience|
|Silent disk corruption|checksum / scrub / replica comparison|目标是检测并恢复|通常透明|
|Software bug|replication 本身也可能传播错误|最危险|formal methods / verification / deployment discipline 降低风险|
|Transaction coordinator crash|durable ledger + recovery|应保持 atomicity|transaction 可能延迟|

# Part 15：为什么“Predictability”这么重要？

假设你的 system：

```
normal:
backend = 1% load

failure:
backend = 100% load
```

这是危险 architecture。

另外一种 system：

```
normal:
backend = 60% load

failure:
backend = 70% load
```

看起来平时效率差一些。

但 failure 时行为非常稳定。

DynamoDB 学到的经验就是：

> **尽量避免 bimodal system。**

也就是：

```
normal mode = one architecture
failure mode = completely different architecture
```

真实 production incident 经常不是：

```
一个 component broke
```

而是：

```
component A failure
  ↓
fallback B
  ↓
B was never sized for this traffic
  ↓
B fails
  ↓
retry storm
  ↓
C fails
  ↓
system-wide outage
```

这比 Raft 的：

```
Leader crash
→ elect new leader
```

更加“production distributed systems”。

Amazon 对 DynamoDB 十年经验的总结也把 predictability、traffic-adaptive partitioning、continuous verification 和 operational discipline 列为主要经验。[Amazon Science](https://www.amazon.science/blog/lessons-learned-from-10-years-of-dynamodb?utm_source=chatgpt.com)

# Part 20：三个粒度总结

## 30 秒版本

DynamoDB 这节课讲的是，一个超大规模 multi-tenant key-value database 怎样同时实现 scalability、availability、predictable performance 和 durability。它通过 partitioning 和 multi-AZ replication 扩展和容错，又通过 global admission control、bursting、adaptive capacity 等解决 workload skew，并强调 predictability over absolute efficiency、continuous data verification。后来 DynamoDB 还加入基于 transaction coordinator 和 timestamp ordering 的 multi-item transactions。

---

# 3 分钟版本

DynamoDB 把 table 根据 partition key 的 hash 拆成很多 physical partitions，并将每个 partition replication 到多个 AZ，以实现 horizontal scalability 和 fault tolerance。

真正困难的是 multi-tenancy。简单把 provisioned capacity 平均分给 partition 会导致 hot partition 即使在 table 总 capacity 足够时仍被 throttle，所以系统逐渐发展出 global admission control、burst capacity 和 adaptive capacity / split for heat，让 resource allocation 和 physical partitioning 跟随 workload。

另一个重要 lesson 是 predictability。一个 99.9% hit 的 cache 可能在 cache failure 时让 backend traffic 瞬间暴涨数百倍，因此 production architecture 不应该让 fallback path 成为平时完全没被 exercised 的弱点。

Durability 方面，多副本并不够，因为 corruption 和 software bugs 可以被 replication 一起复制，所以 DynamoDB 使用 checksum、WAL archive、scrubbing 和 continuous verification。

最后，它在 KV model 上增加 distributed transactions，通过 transaction coordinator、durable ledger 和 timestamp ordering 支持 atomic / serializable multi-item operations。
