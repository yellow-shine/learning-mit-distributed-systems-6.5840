你这里混淆了两种完全不同的 “replica”。Aurora 论文里确实都叫 replica，但层次不同。

最关键的区分是：

```
6 个 replicas
=
Storage replicas

Aurora Read Replica
=
Database / Compute replica
```

它们不是一回事。

可以把整个 Aurora 看成两层：

```
                  Aurora Cluster
                        │
        ┌───────────────┴────────────────┐
        │                                │
     Compute Layer                  Storage Layer
        │                                │
   ┌────┴─────┐                  一个 PG 的 6 份数据
   │          │                         │
 Writer     Reader               AZ-A   AZ-B   AZ-C
 instance  instance              A1 A2   B1 B2   C1 C2
```

## 1. 你说的“6 个 replica”是什么？

上一节讲的：

```
V = 6
Vw = 4
Vr = 3
```

这里的 6 个 replica 指的是：

> **同一个 10GB segment 的 6 个 storage copies。**

例如 PG42：

```
PG42

AZ-A            AZ-B            AZ-C

Storage A1      Storage B1      Storage C1
Storage A2      Storage B2      Storage C2
```

这 6 份属于 Aurora 的**分布式存储层**。

它们保存：

```
redo logs
materialized pages
page versions
...
```

它们不是 MySQL/PostgreSQL 数据库实例，也不会直接接收：

```
SELECT * FROM users;
```

---

## 2. Aurora Read Replica 是什么？

Read Replica 是一个真正运行：

```
MySQL / PostgreSQL compatible DB engine
```

的 **compute instance**。

例如：

```
                    Aurora Cluster

             ┌───────────────┐
             │ Writer        │
             │ DB Instance   │
             └───────┬───────┘
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       Reader1    Reader2    Reader3
       DB Inst    DB Inst    DB Inst

                     │
                     ▼
             Shared Storage Volume
```

用户可以：

```
Writer endpoint
→ INSERT / UPDATE / DELETE / SELECT

Reader endpoint
→ SELECT
```

所以：

> **Read Replica 是用来扩展 SQL read workload 的数据库计算节点。**

---

# 3. 最特别的是：这些 Read Replicas 没有自己的独立数据库副本

这是 Aurora 和传统 MySQL replication 很大的区别。

传统 MySQL：

```
Primary MySQL
    │
    │ binlog
    ▼
Replica MySQL
    │
    ▼
自己的 storage
```

所以每个 replica 基本都有：

```
一整份数据库副本
```

例如：

```
Primary
 └── 1 TB storage

Replica1
 └── 1 TB storage

Replica2
 └── 1 TB storage
```

但 Aurora：

```
Writer ──────┐
Reader1 ─────┤
Reader2 ─────┼── Shared Aurora Storage
Reader3 ─────┘
```

所有 DB instances 共享：

> **同一个 Aurora distributed storage volume。**

所以不是：

```
Writer → storage copy A

Reader1 → storage copy B

Reader2 → storage copy C
```

而是：

```
                Shared Logical Volume

                  PG1 PG2 PG3...
                  │
Writer ───────────┤
Reader1 ──────────┤
Reader2 ──────────┤
Reader3 ──────────┘
```

然后每个 PG 在底层又有：

```
6 storage replicas
```

这是两个完全不同的 replication layer。

---

# 4. 所以 Aurora 实际上有“两层 replication”

这个 mental model 很重要。

### 第一层：Storage Replication

为的是：

```
Durability
Availability
Fault tolerance
```

结构：

```
PG
│
├── AZ-A
│   ├── storage replica A1
│   └── storage replica A2
│
├── AZ-B
│   ├── storage replica B1
│   └── storage replica B2
│
└── AZ-C
    ├── storage replica C1
    └── storage replica C2
```

这里才有：

```
4/6 write quorum
3/6 read quorum
```

---

### 第二层：Compute / DB Replication

为的是：

```
read scaling
failover
high availability
```

例如：

```
Writer DB instance

Reader DB instance 1
Reader DB instance 2
Reader DB instance 3
```

这些就是 AWS 控制台里的：

```
Aurora Replicas
```

也就是大家通常说的：

```
read replicas
```

---

# 5. 那 Reader Instance 自己存什么？

它自己当然也有内存：

```
Buffer Pool
Query execution state
Connections
Locks / metadata
...
```

例如：

```
Reader1

Buffer Pool
├── Page 100
├── Page 500
└── Page 900
```

Writer 修改 Page 500：

```
Page500:
balance 1000 → 900
```

生成：

```
redo LSN 10001
```

redo 一方面：

```
Writer
   │
   └──→ Storage 6 replicas
```

另一方面论文描述还会把：

```
redo + metadata
```

stream 给 Aurora read replicas：

```
                Writer
                  │
            redo stream
        ┌─────────┼─────────┐
        ▼         ▼         ▼
     Reader1   Reader2   Reader3
```

Reader1 如果自己的 buffer cache 中恰好有 Page500：

```
Page500 old version
+
redo
↓
Page500 new version
```

所以 Reader 的 buffer cache 可以快速跟上 Writer。

---

# 6. 如果 Reader buffer cache 没这个 page 呢？

例如：

```
SELECT *
FROM users
WHERE id = 42;
```

Reader1 发现：

```
Page500
```

不在自己的 buffer pool。

那么它就：

```
Reader1
   │
   │ read Page500
   ▼
Shared Aurora Storage
```

storage 返回正确版本。

然后：

```
Reader1 buffer pool

Page500
```

以后再读就可以直接从 cache 返回。

---

# 7. 那你说的 “read 3/6” 是不是 Reader 每次读都去问 3 个 storage node？

这是一个特别容易产生的误解。

不要简单理解成：

```
SELECT
  ↓
Reader DB
  ↓
同时读取 3 个 storage replicas
  ↓
比较结果
```

**不是这个意思。**

论文 Section 2 里的：

```
Vr = 3
```

首先是在描述 storage replication 的 quorum **正确性和容错模型**：

```
V = 6
Vw = 4
Vr = 3
```

满足：

```
Vr + Vw > V

3 + 4 > 6
```

保证 read quorum 与最近 write quorum 有交集。

它的重要意义之一是：

```
如果只剩 3 个有效 storage copies

仍然有足够的信息确认正确状态
并能够重建新的副本
```

并不意味着 SQL 层的每个普通页面读取都必须：

```
fan-out 到 3 台机器
```

Aurora 实际读路径会尽量从已知拥有所需 page/version 的 storage node 获取，而不是每次 SELECT 都做一次昂贵的 3-way voting。

所以这里最好分开理解：

```
3/6 read quorum

≠

三个 Aurora Read Replicas

≠

每次 SELECT 必须读三个节点
```

# 8. 举一个完整例子

假设你创建：

```
Aurora Cluster

1 Writer
2 Readers
```

看起来：

```
Compute layer:

Writer
Reader1
Reader2
```

底下：

```
Storage layer:

PG1:
A1 A2 B1 B2 C1 C2

PG2:
A1 A2 B1 B2 C1 C2

PG3:
A1 A2 B1 B2 C1 C2
...
```

注意这里不是：

```
总共只有 6 个 storage servers
```

而是逻辑上每一个 PG：

```
有 6 个 segment replicas
```

这些 replicas 会分布在庞大的 storage fleet 上。

---

假设 Writer：

```
UPDATE account
SET balance = 900
WHERE id = 42;
```

生成：

```
redo LSN=100
```

这个 page 属于：

```
PG7
```

于是：

```
                 redo100
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼

      AZ-A         AZ-B         AZ-C
      A1 A2        B1 B2        C1 C2
```

收到：

```
A1 ✓
A2 ✓
B1 ✓
C1 ✓
```

已经：

```
4/6
```

所以：

```
redo durable
transaction commit
```

与此同时：

```
Writer
  │
  │ redo100
  ├────────→ Reader1
  └────────→ Reader2
```

Reader 可以更新自己的 buffer cache。

然后用户：

```
SELECT balance
FROM account
WHERE id = 42;
```

请求发到：

```
Reader1
```

如果 page 已经在 Reader1 cache：

```
直接返回 900
```

如果不在：

```
Reader1
   ↓
Aurora shared storage
   ↓
取 Page
   ↓
放入自己的 buffer cache
   ↓
返回 900
```

# 9. 为什么 Aurora 要同时有这两层？

因为解决的是完全不同的问题。

你可以这样记：

|Replica|位于哪里|解决什么问题|
|---|---|---|
|6-way Storage Replica|Storage Layer|数据不丢、AZ 容灾、durability|
|Aurora Read Replica|Compute Layer|SELECT 扩展、故障切换、降低 writer 压力|

所以：

```
Storage replicas
```

回答的是：

> **我的数据有几份？机器/AZ 挂了还能不能找回来？**

而：

```
Read replicas
```

回答的是：

> **谁来执行 SELECT？一个 DB instance 扛不住读流量怎么办？**

# 10. 用 Kubernetes 类比会特别直观

你可以把 Aurora 想成：

```
                     PVC / Distributed Storage
                              │
          ┌───────────────────┴──────────────────┐
          │                                      │

DB Pods / Compute                     Storage internal replicas

writer pod                              copy1
reader pod 1                            copy2
reader pod 2                            copy3
                                        copy4
                                        copy5
                                        copy6
```

当然 Aurora 并不是 Kubernetes PVC 的具体实现，但概念上很好理解：

```
Reader DB Instance
≈ compute replica / DB pod

6 storage replicas
≈ storage system 内部的数据副本
```

**千万不要把它们看成同一层。**

一句话记忆：

> **Aurora 的 “6 replicas” 是数据的六份存储副本；Aurora Read Replica 是额外的数据库计算实例。多个 Writer/Reader DB instances 共享同一个底层 Aurora distributed storage，而这个 storage 内部又对每个 segment 做 6-way replication。**
