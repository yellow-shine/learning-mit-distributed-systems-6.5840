这一节 **“The Log is the Database”** 是 Aurora 论文里最重要的一节之一。

如果上一节 Section 2 解决的是：

> **数据应该复制几份、放在哪里、坏几个还能活？**

那么 Section 3 解决的是：

> **既然每份数据要复制 6 份，如果还按照传统 MySQL 的方式写磁盘，网络和 I/O 岂不是爆炸？**

Aurora 的答案非常大胆：

> **数据库节点不要再往存储层写 data page，只把 redo log 发给 storage。Storage 自己根据 redo log 生成 page。**

这就是标题：

# The Log Is the Database

可以先记住下面这个对比：

```
Traditional DB

SQL
 ↓
modify memory page
 ↓
├── write redo log
├── write binlog
├── write data page
├── write doublewrite page
├── write metadata
└── checkpoint pages
        ↓
      Storage
```

Aurora：

```
SQL
 ↓
modify memory page
 ↓
generate redo
 ↓
     REDO ONLY
         ↓
 ┌──── Storage ─────┐
 │                  │
 │ redo → data page │
 │                  │
 └──────────────────┘
```

数据库主机的网络 write path 被极大简化了。

# 1. 先从问题开始：6 副本虽然安全，但代价是什么？

上一节我们已经知道：

```
3 AZ

AZ-A        AZ-B        AZ-C
A1 A2       B1 B2       C1 C2

6 replicas
write quorum = 4/6
```

这在可靠性上很好。

可是如果传统 MySQL 一次事务本来就产生很多 I/O，然后每个 I/O 再复制 6 份：

```
应用的一次 UPDATE
    ↓
很多 DB I/O
    ↓
每个 I/O × 6
    ↓
大量 network packets
```

这就是论文说的：

> Amplified Writes

或者叫：

**写放大。**

---

# 2. 为什么传统数据库一次 UPDATE 不只是“写一次数据”？

假设：

```
UPDATE account
SET balance = 900
WHERE id = 1;
```

用户脑子里的模型可能是：

```
balance = 1000
        ↓
balance = 900
        ↓
写一次磁盘
```

实际数据库远复杂得多。

MySQL/InnoDB 可能涉及：

```
             UPDATE
                │
                ▼
          modify buffer page
                │
       ┌────────┼─────────┐
       ▼        ▼         ▼
     redo     binlog    dirty page
                         │
                         ▼
                    doublewrite
```

论文中特别列出了：

- redo log
- binary log
- modified data pages
- double-write buffer
- metadata / FRM files

也就是说：

```
一个逻辑变化
```

被以很多形式写了很多遍。

# 3. 为什么需要 redo log？

这个你前面已经学过了。

内存中：

```
Page before

balance = 1000
```

执行：

```
balance = 900
```

生成 redo：

```
page X
offset Y
1000 → 900
```

于是：

```
old page
+
redo
=
new page
```

概念上：

```
Before Image
    +
Redo Record
    ↓
After Image
```

因此真正重要的一点是：

> **redo 本身已经包含了“如何把旧页面变成新页面”的信息。**

Aurora 正是抓住了这一点。

---

# 4. 为什么传统数据库还要写 page？

因为传统数据库的架构通常是：

```
Database Engine
    │
    ├── Buffer Pool
    │     Page X(new)
    │
    └── WAL
          redo
```

事务 commit 时：

```
redo 必须 durable
```

但是：

```
data page 不必立刻写
```

因为 WAL 保证：

```
即使 page 还没落盘
↓
crash
↓
可以 redo
↓
重新得到 page
```

所以：

```
COMMIT

redo    → 必须持久化
page    → 可以稍后持久化
```

这就是经典 WAL。

# 5. 传统 MySQL 的问题：后来终究还是得写 page

虽然 commit 时 page 可以不马上写，但是：

```
dirty page
```

最终必须通过：

```
background flush
checkpoint
buffer eviction
```

写到磁盘。

于是数据库节点最终还是要产生：

```
redo writes
+
page writes
```

甚至：

```
doublewrite
binlog
metadata
...
```

这就是 Aurora 想消掉的东西。

# 6. 为什么 doublewrite 又多写了一遍？

这是个很典型的例子。

假设数据库 page：

```
16 KB
```

底层存储不保证一次 16KB write 原子完成。

可能 crash 发生在中间：

```
old page:

AAAAAAAAAAAAAAAA

write new page:

BBBBBBBBBBBBBBBB

crash halfway

结果:

BBBBBBBBAAAAAAAA
```

这就是：

> torn page

所以 InnoDB 传统上会先写：

```
doublewrite buffer
```

再写真正 data page。

相当于：

```
page
 ↓
temporary safe copy
 ↓
real location
```

于是同一个信息：

```
又写了一次
```

Aurora 的一个重要观点就是：

> 很多传统数据库机制，是为了弥补底层 storage 不理解数据库语义而产生的。

既然 Aurora 自己控制 storage：

```
Database-aware storage
```

很多这样的重复工作就可以重新设计。

```
           │                              │
           ▼                              ▼
          EBS                            EBS
```

一次 write 大概经历：

```
Primary
  │
  │ 1
  ▼
EBS
  │
  │ 2 local replication
  ▼
EBS mirror

  │
  │ 3 cross-AZ software mirroring
  ▼

Standby
  │
  │ 4
  ▼
EBS
  │
  │ 5 local replication
  ▼
mirror
```

问题不仅是：

```
写得多
```

而且还是：

```
很多步骤串行同步
```

# 8. 为什么“串行同步”非常糟糕？

假设一次 commit 需要经过：

```
A = 1 ms
B = 2 ms
C = 3 ms
```

如果串行：

```
A → B → C

latency ≈ 1 + 2 + 3
        = 6 ms
```

而如果可以并行：

```
        ┌→ A 1ms
request ├→ B 2ms
        └→ C 3ms
```

理论上接近：

```
max(A,B,C)
=
3 ms
```

Aurora 非常强调：

> 不仅要减少 I/O 数量，还要减少同步点。

---

# 9. Jitter 又是什么问题？

假设平时：

```
node1 = 1ms
node2 = 1ms
node3 = 1ms
node4 = 1ms
```

偶尔某个节点：

```
node4 = 50ms
```

如果系统要求：

```
4/4
```

那么：

```
latency = 50ms
```

因为必须等最慢的。

这种偶发慢请求就是：

> jitter / tail latency

传统同步镜像架构从分布式系统角度可以理解为：

```
4/4 quorum
```

也就是：

```
ALL replicas must succeed
```

Aurora 则：

```
4/6
```

所以：

```
6 nodes:

A 1ms
B 1ms
C 2ms
D 2ms
E 50ms
F timeout
```

只等：

```
A B C D
```

即可。

```
E F
```

不在 foreground critical path。

这就是为什么 Section 2 的 quorum 设计不仅提高 availability：

> **它同时降低 tail latency。**

# 10. Aurora 的关键改变：数据库只写 REDO

现在进入 Section 3.2 的核心。

传统：

```
DB Engine
    │
    ├── redo → storage
    │
    └── page → storage
```

Aurora：

```
DB Engine
    │
    └── REDO ONLY
            │
            ▼
        Storage
            │
            ▼
        apply redo
            │
            ▼
         data page
```

论文说得非常绝对：

> No pages are ever written from the database tier.

也就是：

```
checkpoint        → 不从 DB 节点写 page
background flush  → 不从 DB 节点写 page
buffer eviction   → 不从 DB 节点写 page
```

DB 层只发送：

```
redo log records
```

# 11. 那么 data page 到底由谁生成？

Storage node。

原来数据库里有：

```
Log Applicator
```

做：

```
old page
+
redo
↓
new page
```

Aurora 把这个逻辑下推到了：

```
Storage Service
```

所以架构变成：

```
             DB Engine

           generate redo
                │
                ▼
       ┌─────────────────┐
       │ Storage Service │
       │                 │
       │ old page        │
       │    +            │
       │ redo records    │
       │    ↓            │
       │ new page        │
       └─────────────────┘
```

这就是：

> offloading redo processing to storage

---

# 12. 为什么叫“The Log is the Database”？

这是最需要真正理解的一句话。

传统思维：

```
Data Page = 真正的数据
Log       = crash recovery 辅助信息
```

Aurora 把关系几乎反过来了：

```
Redo Log = authoritative history / durable state
Page     = redo 应用后的 materialized result
```

可以把它理解成：

```
Page
=
f(previous page, redo records)
```

甚至概念上：

```
Database State
=
Initial State
+
Redo1
+
Redo2
+
Redo3
+
...
```

所以：

> **page 是 log 计算出来的结果。**

这和你熟悉的 event sourcing 很像：

```
Events
  ↓
replay
  ↓
Current State
```

例如：

```
AccountCreated
Deposit(1000)
Withdraw(100)
```

当前余额：

```
900
```

900 可以看成 event stream 的 materialized state。

Aurora：

```
redo stream
   ↓
apply
   ↓
page
```

非常类似。

# 13. 但难道每次读 page 都从“宇宙大爆炸”开始 replay？

当然不能。

假设 Page 42 修改过：

```
1,000,000 次
```

如果每次读取：

```
Page42 initial version
+
redo1
+
redo2
+
...
+
redo1,000,000
```

肯定不可接受。

所以 Aurora 会：

> background materialization

例如：

```
Page42@LSN100
   +
redo101
redo102
...
redo200
   ↓
Page42@LSN200
```

然后保存：

```
Page42@LSN200
```

之后就不必从 LSN 0 开始。

# 14. 因此 storage 实际上保存两类东西

可以这样理解：

```
Storage Node

┌──────────────────────┐
│ Materialized Pages   │
│                      │
│ Page X @ LSN 800     │
│ Page Y @ LSN 920     │
└──────────────────────┘

+
  
┌──────────────────────┐
│ Redo Records         │
│                      │
│ Page X: 801..850     │
│ Page Y: 921..925     │
└──────────────────────┘
```

如果 DB 请求 Page X@850：

```
Page X@800
+
redo 801..850
    ↓
Page X@850
```

这就是：

> on-demand materialization

# 15. 为什么论文说 materialized page 只是“cache”？

这句话非常重要：

> pages that the storage system materializes are simply a cache of log applications

不是说 page 不重要。

而是从 correctness 的角度：

```
redo 有了
+
某个旧版本 page 有了
```

那么：

```
最新 page
```

就能重新算出来。

因此：

```
materialized page
```

本质上是：

```
避免重复计算的缓存结果
```

Mental model 可以变成：

```
redo log
   │
   │ authoritative history
   ▼
apply redo
   │
   ▼
materialized page
   │
   └── performance optimization
```

# 16. 这和传统 Checkpoint 有什么区别？

这是论文一个非常漂亮的点。

传统 DB 的 redo log 类似：

```
checkpoint
     │
     ▼
LSN 1000
     │
     ├── redo1001
     ├── redo1002
     ├── ...
     └── redo100000
```

log 越来越长。

最终必须：

```
把大量 dirty pages 刷盘
```

推进 checkpoint。

所以 checkpoint 是一个相对**全局的概念**：

```
整个 redo history
```

有多长。

---

Aurora 不一样。

它关心的是：

```
每一个 page 自己的 redo chain
```

例如：

```
Page A

materialized @ 100
redo 101
redo 102
redo 103
```

只有 3 条。

而：

```
Page B

materialized @ 100
redo 101
...
redo 10000
```

B 的 chain 很长。

Aurora 可以只 materialize：

```
Page B
```

不必：

```
为了 checkpoint
把所有 dirty pages 一起写
```

所以是：

```
Traditional:

global log age
   ↓
checkpoint many pages
```

Aurora：

```
per-page log chain length
   ↓
materialize hot/long-chain page
```

这是非常大的架构区别。

# 17. 一次 Aurora write 到底怎样走？

把前面你学到的 PG、LSN 和 quorum 连接起来。

假设事务修改：

```
Page A
Page B
Page C
```

DB Engine 生成：

```
LSN 1001
LSN 1002
LSN 1003
...
```

redo 是：

```
fully ordered
```

然后根据 page 所属的：

```
logical segment / PG
```

进行 batch。

例如：

```
PG10:
  LSN1001
  LSN1003
  LSN1005

PG27:
  LSN1002
  LSN1004
```

然后每个 batch：

```
             PG10

               │
     ┌─────────┼─────────┐
     ▼         ▼         ▼
    AZ-A      AZ-B      AZ-C
    A1 A2     B1 B2     C1 C2
```

同时发送给：

```
6 replicas
```

不是串行：

```
A → B → C → D → E → F
```

而是并行：

```
       ┌→ A1
       ├→ A2
redo ──┼→ B1
       ├→ B2
       ├→ C1
       └→ C2
```

DB 等：

```
4 ACK
```

就认为：

```
redo durable / hardened
```

# 18. “Hardened”是什么意思？

论文里经常出现：

```
hardened log record
```

你可以直接理解：

> **这个 redo 已经满足 durable quorum，即使部分机器挂掉也不会丢。**

也就是：

```
redo generated
    ↓
send 6 replicas
    ↓
4 persisted
    ↓
HARDENED
```

这和我们前面讲的：

```
Durable LSN / Durable Frontier
```

直接有关。

例如：

```
LSN 1001 ✓ 4/6
LSN 1002 ✓ 4/6
LSN 1003 ✓ 4/6
```

那么这段 log 就已经 durable。

# 19. Aurora 的 read replica 怎么办？

论文中的 Aurora cluster：

```
                Primary
                   │
          redo + metadata
         ┌─────────┼─────────┐
         ▼         ▼         ▼
      Replica1  Replica2  Replica3
                   │
                   ▼
            Shared Storage
```

Primary：

```
修改 buffer pool
生成 redo
```

然后：

1. redo 发送到 storage；
2. redo 也流向 Aurora read replicas。

read replica 收到 redo 后：

```
apply redo
    ↓
更新自己的 buffer cache
```

因此它不需要像传统 MySQL replica 那样：

```
完整重放 SQL/binlog
+
维护一份完整独立 storage copy
```

大家底下共享 Aurora distributed storage。

# 20. 为什么网络流量能少这么多？

这是 Section 3 最核心的性能收益。

传统：

```
一个 transaction

redo
+
binlog
+
data pages
+
doublewrite pages
+
metadata
+
replication
```

Aurora：

```
一个 transaction

redo
```

虽然 redo：

```
× 6 replicas
```

但是 redo 本身非常小。

假设修改一个：

```
16 KB page
```

只改：

```
balance: 1000 → 900
```

传统可能最终传输整个：

```
16KB page
```

Aurora可能只发送类似：

```
Page=42
Offset=1234
Length=8
NewBytes=...
```

当然真实 redo 格式更复杂，但数量级思想就是：

> **传“变化”比传“整个 page”便宜。**

所以即使：

```
redo × 6
```

也可能比：

```
page + redo + doublewrite + replication...
```

便宜得多。

# 21. 论文里的 benchmark 怎么理解？

Table 1：

||Transactions|I/O / Transaction|
|---|---|---|
|Mirrored MySQL|780,000|7.4|
|Aurora|27,378,000|0.95|

30 分钟里：

```
Aurora:
27.378M

MySQL:
0.780M
```

大约：

```
35×
```

吞吐差异。

而 DB node 侧每 transaction：

```
MySQL = 7.4 I/O
Aurora = 0.95 I/O
```

约：

```
7.7× fewer
```

论文想证明的不是一个普适的“任何 workload Aurora 都正好快 35 倍”，而是：

> **把 page I/O 和大量同步复制移出 database foreground path，架构上的网络负担可以下降一个数量级。**

# 22. 这里有一个很反直觉的结论

Aurora：

```
6 copies
```

传统 MySQL：

```
看起来 replicas 更少
```

结果 Aurora 网络压力反而更低。

为什么？

因为最重要的不是：

```
复制多少份
```

而是：

```
你复制的到底是什么？
```

如果复制：

```
16KB pages × 很多种 write
```

很贵。

如果复制：

```
small redo records
```

即使复制 6 份：

```
依然可能更便宜
```

所以可以记：

> **Aurora 用“减少每次复制的数据量”，换来了“更激进的副本数量”。**

这是 Section 2 和 Section 3 的重要联系：

```
less network write
       ↓
can afford 6 replicas
       ↓
better durability
+
better availability
```

# 23. Crash Recovery 为什么变得特别快？

这是另一个极大的收益。

传统数据库 crash：

```
DB crash
   ↓
restart
   ↓
find checkpoint
   ↓
read redo log
   ↓
replay redo
   ↓
repair pages
   ↓
database ready
```

假设 checkpoint：

```
LSN 1,000,000
```

crash 时：

```
LSN 5,000,000
```

启动可能要 replay：

```
4,000,000 redo records
```

所以恢复时间取决于：

```
checkpoint age
```

# 24. Aurora 不需要在启动时集中做这件事

因为 storage 一直在做：

```
redo
 ↓
persist
 ↓
materialize pages asynchronously
```

假设 DB crash 了。

新的 DB instance 启动：

```
New DB Instance
       │
       ▼
Aurora Storage
```

storage 已经拥有：

```
durable redo
```

所以没有：

```
STOP EVERYTHING

先 replay 整个 database redo history
```

这个步骤。

# 25. 如果某个 page 还没 materialize 到最新怎么办？

那就在读的时候补。

例如：

```
Page A materialized @ LSN 900

redo:
901
902
903
...
950
```

DB 请求：

```
Page A @ 950
```

storage：

```
Page@900
+
redo901..950
↓
Page@950
```

于是 crash recovery 被：

```
一个巨大的 startup job
```

拆成：

```
很多很小的 lazy repair jobs
```

分散在正常请求过程中。

论文说：

> crash recovery is spread across all normal foreground processing.

这句话非常重要。

# 26. 所以 Aurora 的 crash recovery 思想是什么？

传统：

```
          CRASH
            │
            ▼
    giant recovery phase
            │
            ▼
       service ready
```

Aurora：

```
          CRASH
            │
            ▼
       restart quickly
            │
            ▼
normal requests
 │    │    │    │
 ▼    ▼    ▼    ▼
lazy redo applications
```

也就是：

> **把一次性的巨大 recovery 工作摊平到正常运行阶段。**

这和 Section 2 的思想其实很像：

```
大块 repair
   ↓
拆成 10GB segment repair
```

Section 3：

```
巨大 crash recovery
   ↓
拆成 per-page redo application
```

Aurora 很多设计都体现了这种：

> **把 global synchronized work 拆成大量 independent local work。**

# 27. Section 3.3 又在解决什么？

现在已经有：

```
DB → redo → storage
```

但是 storage node 收到 redo 后仍然要干很多事情：

```
persist
repair missing log
build pages
GC
backup
checksum
...
```

如果这些事情全挡在 foreground：

```
commit
```

前面，还是会很慢。

所以 Aurora 又定了一个原则：

> **foreground path 要尽可能短。**

# 28. Storage node 的 foreground path 只有两步

论文 Figure 4：

```
1. receive redo
   ↓
2. persist redo + ACK
```

```
       ↓
```

```
       ↓
```

```
       ↓

    ↓
```

# 37. 如果后台真的积压太严重怎么办？

当然不能无限拖。

比如：

```

```

越来越大。

```

```

防止 queue 无限增长。

```

```

一个 storage node 慢了，只影响分散的 segments。

而 4/6 quorum 又允许：


先不等它。

# 39. “The Log Is the Database” 最准确的 mental model

我建议你不要把它简单理解成：

> Aurora 没有 data pages。

这是错的。

Aurora **当然有 pages**。

更准确的是：

```
                Source of truth
                     │
                     ▼
                 Redo Log
                     │
               apply/materialize
                     │
                     ▼
                  Pages
                     │
            performance cache
```

所以：

> **Redo log 是持久化状态变化的 authoritative representation；page 是这些变化应用后的 materialized representation。**

实际系统为了性能当然不会永远从最初 redo 开始重建，而是持续：

```
redo chain
   ↓
materialize
   ↓
new base page
```

# 40. 和你前面学的 LSN / Durable Frontier 连接起来

现在前面那些概念应该开始连起来了。

比如 DB 生成：

```

LSN 101
LSN 102
LSN 103
LSN 104
```

每条被发送给所属 PG 的：

```
6 replicas
```

当：

```
LSN100 → 4/6
LSN101 → 4/6
LSN102 → 4/6
```

都已经满足 quorum，就进入：

```
durable state
```

Storage 又可能是：

```
Page A materialized @ LSN80
+
redo 81..102
```

所以：

```
Durable Frontier
```

回答：

> 哪些 log 已经安全地存下来了？

而：

```

```

回答：

> 某个 page 已经把 redo 应用到了哪里？

这两个完全不是一回事：

```
durability progress
≠
page materialization progress
```

这是理解 Aurora 非常关键的一点。

# 41. 最后用一个例子彻底串起来

用户执行：

```
UPDATE users
SET balance = 900
WHERE id = 42;
COMMIT;
```

Aurora primary：

```
① Page 17 在 buffer cache

balance=1000
       ↓
balance=900
```

生成：

```
② redo

LSN=500
Page=17
change=...
```

根据 Page17 找到：

```
③ PG7
```

然后：

```
④ redo500 并行发给 PG7 的六个 replicas

          ┌→ A1
          ├→ A2
redo500 ──┼→ B1
          ├→ B2
          ├→ C1
          └→ C2
```

收到：

```
A1 ✓
A2 ✓
B1 ✓
C1 ✓

B2 ...
C2 ...
```

已经：

```
4/6
```

所以：

```
⑤ redo500 hardened
```

事务可以 commit。

注意：

> 到这里可能还没有任何 storage node 把新的完整 Page17 写出来。

没关系。

稍后 storage：

```
⑥ Page17@450
+
redo451..500
↓
Page17@500
```

保存 materialized page。

甚至如果还没来得及做：

```
DB read Page17
```

storage 可以：

```
on demand apply redo
```

得到：

```
Page17@500
```

因此：

```
correctness
```

不依赖于：

```
page 是否已经 background materialized
```

只依赖：

```
redo 是否 durable
```

这就是：

# The Log Is the Database

如果把整节只压缩成一句话：

> **传统数据库把 WAL 当作恢复 data page 的辅助日志；Aurora 则把 durable redo 提升成核心持久化表示，让 storage 根据 redo 异步生成 data pages。于是数据库前台只需要发送很小的 redo，并行写 6 份等 4 份 ACK，而 page flush、checkpoint、repair、backup、GC 等大量工作都移出 commit critical path。**

而这其实也是 Aurora 整篇论文最核心的架构转变：

```
传统：

Compute owns database state
Storage stores blocks


Aurora：

Compute executes transactions
Storage understands database history
```

后面再看到 **LSN、VCL、CPL、durable LSN、segment completeness、read point** 时，基本都可以从这个 mental model 往下推。
