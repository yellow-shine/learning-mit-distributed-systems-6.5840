这一节 **“THE LOG MARCHES FORWARD”** 可以看成 Aurora 论文里最关键的一节之一。

第 3 节回答的是：

> **为什么 Aurora 只把 redo log 当成真正需要同步写入存储层的数据。**

第 4 节进一步回答：

> **既然整个数据库都由一条不断向前推进的 redo log 驱动，那么 writer、6 份存储副本、read replica、事务 commit、读请求以及 crash recovery，怎么知道“现在安全到哪里了”？**

Aurora 的答案非常漂亮：

> 不要每次搞一次分布式事务去协调所有节点，而是维护若干个**单调向前推进的 LSN 水位线**。

其中最重要的是：

```
LSN
 ↓
SCL   某个 storage segment 完整到哪里
 ↓
VCL   整个 Volume 连续完整到哪里
 ↓
CPL   哪些位置允许作为一致性切点
 ↓
VDL   整个 Volume 真正可以安全承诺到哪里
```

理解了这些，你基本就理解了整节。

---

# 一、先建立最重要的 Mental Model

你可以把 Aurora 看成下面这样：

```
                    Database Writer
                          │
                     generate redo
                          │
                          ▼
              LSN 100, 101, 102, 103...
                          │
              ┌───────────┴───────────┐
              │                       │
              ▼                       ▼
       Storage Service           Read Replicas
        6-way replicated       update buffer cache
              │
              ▼
      redo → materialized page
```

这里真正的「数据库」从持久化角度已经不是 data page，而是：

```
有序 redo log
```

data page 更像：

```
redo log 的 materialized / cached result
```

于是 Aurora 的核心问题变成：

> redo log 到底可靠地推进到哪个 LSN 了？

这就是标题：

> **The Log Marches Forward**

日志不断向前走，系统状态也跟着一组 frontier 向前走。

---

# 二、先把这一节所有 LSN 一次搞清楚

这是最重要的一张表：

|名字|作用范围|含义|
|---|---|---|
|**LSN**|Volume|每条 redo record 的全局递增编号|
|**CPL**|MTR|可以安全截断/恢复的一致性边界|
|**SCL**|一个 storage segment|这个 segment 的日志完整到哪里|
|**VCL**|整个 Volume|整个 Volume 的日志连续完整到哪里|
|**VDL**|整个 Volume|真正允许作为 durable state 的位置|
|**LAL**|Writer|writer 最多允许领先 VDL 多远|
|**Read Point**|一次 read|这次 read 要观察哪个 LSN 的数据库|
|**PGMRPL**|Protection Group|所有 reader 中最老还可能需要的 LSN|

最关键的关系：

```
VDL <= VCL
```

并且：

```
VDL 必须是一个 CPL
```

所以可以理解成：

```
VCL = 物理上完整到哪里
VDL = 逻辑上允许承诺到哪里
```

这两个区别极其重要。

---

# 三、为什么 VCL 和 VDL 不能是同一个东西？

论文给了这个例子：

```
CPL:

900
1000
1100

当前 storage 已经完整拥有：

LSN <= 1007
```

那么：

```
VCL = 1007
```

但是：

```
VDL = 1000
```

为什么？

因为：

```
1001 ... 1100
```

可能属于同一个 MTR。

现在只收到：

```
1001 ... 1007
```

如果恢复到 1007：

```
MTR 被执行了一半
```

这可能让 B-Tree、page metadata 等内部结构进入不一致状态。

所以只能退到上一个合法 consistency point：

```
              VCL
               ↓
900    1000    1007       1100
 |------|-------|-----------|
CPL    CPL                  CPL
        ↑
       VDL
```

因此：

> **VCL 解决“日志有没有丢”。**
> 
> **CPL 解决“这个位置是不是一个合法数据库状态”。**
> 
> **VDL = 两者结合后的安全恢复点。**

---

# 四、CPL 从哪里来？MTR 是关键

这里千万不要把：

```
MTR
```

和：

```
SQL Transaction
```

混为一谈。

一个用户事务可能是：

```
BEGIN;

UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;

COMMIT;
```

但数据库内部一次修改 B-Tree page，可能涉及：

```
修改 leaf page
修改 parent page
修改 page header
修改 metadata
```

这些必须作为一个很小的原子操作完成。

这就是：

```
Mini Transaction
MTR
```

关系大致是：

```
User Transaction
│
├─ MTR 1
│   ├─ log 100
│   ├─ log 101
│   └─ log 102 ← CPL
│
├─ MTR 2
│   ├─ log 103
│   └─ log 104 ← CPL
│
└─ MTR 3
    ├─ log 105
    ├─ log 106
    └─ log 107 ← CPL
```

所以 CPL 的本质是：

> **到这里为止，数据库内部结构处于一个可以被观察、恢复的完整状态。**

这就是为什么恢复不能随便停在：

```
LSN 101
```

而必须停：

```
102
```

# 五、这为什么能避免 2PC？

这是 4.1 最值得理解的地方。

假设用一种 naive 方案。

一个 MTR 修改了多个 storage segment，你可能设计：

```
Database
   │
   ├── PREPARE → storage A
   ├── PREPARE → storage B
   ├── PREPARE → storage C
   │
   │ wait...
   │
   ├── COMMIT → storage A
   ├── COMMIT → storage B
   └── COMMIT → storage C
```

这就越来越接近：

```
2PC
```

问题是消息很多，而且 coordinator crash 会变得麻烦。

Aurora 换了个问题：

> 我为什么非要让所有 storage node 在这一刻共同宣布 COMMIT？

它让所有东西只是：

```
append redo
```

storage node 收到以后：

```
append
ack
repair missing logs
materialize pages
```

writer 根据 ack 不断推进：

```
VCL
VDL
```

所以 Aurora 不需要：

```
PREPARE
COMMIT
```

这种针对每个小操作的同步协议。

而变成：

```
send redo
      ↓
collect quorum ACK
      ↓
advance frontier
```

本质上是：

> **把“每次达成一致”转换成“单调推进一个已经达成一致的前缀”。**

这就是 ordered log 带来的巨大优势。

注意，这不是说 Aurora **完全没有协调**。

它依然有：

```
write quorum
ordered LSN
CPL
recovery quorum
```

只是没有让 storage tier 为每个 MTR 跑一次完整的 2PC。

# 六、SCL：为什么 storage node 能知道自己“缺日志”？

这是一个容易忽略、但非常漂亮的设计。

整个 Aurora Volume 有一条全局 LSN：

```
100
101
102
103
104
105
106
...
```

但是一个 PG 只负责 Volume 的一部分 page。

所以 PG-A 可能只关心：

```
100
103
106
```

PG-B 可能只关心：

```
101
104
105
```

因此 PG-A 收到：

```
100
103
```

不能因为没看到：

```
101
102
```

就认为：

> “丢包了！”

因为 101、102 可能本来就属于其他 PG。

所以 redo record 中有一个：

```
backlink
```

它告诉你：

```
这个 PG 的上一条 redo record 是谁
```

例如：

```
LSN 100
   ↓

LSN 103
previous-PG-LSN = 100

   ↓

LSN 106
previous-PG-LSN = 103
```

于是如果 storage 收到：

```
106
```

发现：

```
previous = 103
```

但是本地只有：

```
100
```

它马上知道：

```
缺 103
```

然后通过 PG 内 storage node 之间的 gossip：

```
Node A → “我有没有 103？”
Node B → “有，给你。”
```

修补 hole。

这样每一个 segment 可以维护自己的：

```
SCL
Segment Complete LSN
```

意思可以理解为：

> **对于这个 PG 应该收到的所有 redo，我已经连续完整到哪里。**

# 七、Normal Write：writer 怎么不停向前推进？

正常写路径非常简单。

假设：

```
当前 VDL = 1,000,000
```

writer 不断生成：

```
1,000,001
1,000,002
1,000,003
...
```

并发送到对应的 storage PG。

每收到 write quorum ACK，就可以继续推进 durable frontier。

但是有一个问题：

如果网络突然慢了，而数据库继续疯狂生成 redo：

```
VDL = 1M

writer 已经生成：

100M
```

那 writer 和 storage 的距离就太大了。

因此 Aurora 引入：

```
LAL
LSN Allocation Limit
```

论文里的值是：

```
10,000,000
```

约束是：

```
allocated LSN <= VDL + LAL
```

例如：

```
VDL = 100M

最大只能产生到：

110M
```

如果 storage 跟不上：

```
VDL 不动
```

writer 最终撞上：

```
VDL + LAL
```

然后：

```
throttle writes
```

所以 LAL 本质上就是：

> **storage backpressure。**

---

# 八、Commit 是这一节里非常漂亮的设计

传统直觉可能是：

```
client
   │ COMMIT
   ▼
DB worker
   │
   │ fsync WAL
   │ wait
   │
   ▼
reply
```

worker 会卡在那里等待 durability。

Aurora 不这么做。

假设事务 T：

```
commit LSN = 5000
```

客户端调用：

```
COMMIT;
```

worker 做的事情只是：

```
T.commitLSN = 5000

put T into waiting_commit_queue
```

然后 worker：

```
继续处理别的请求
```

与此同时 background thread 不断看到：

```
VDL
```

往前走。

例如：

```
VDL = 4980
```

还不能回复。

后来：

```
VDL = 5000
```

现在：

```
VDL >= commitLSN
```

于是：

```
Commit Thread
    │
    └── ACK → client
```

所以：

```
transaction durable
    ⇔
VDL >= transaction.commitLSN
```

这就是 Aurora 版本的 WAL durability rule。原论文明确描述了这种异步提交机制。[College of Science](https://www.cs.usfca.edu/~mmalensek/cs677/schedule/papers/verbitski2017aurora.pdf?utm_source=chatgpt.com)

# 九、为什么这比“每个事务 fsync”好？

假设同时有：

```
Tx A: commitLSN = 5001
Tx B: commitLSN = 5005
Tx C: commitLSN = 5010
Tx D: commitLSN = 5012
```

VDL 原来：

```
5000
```

然后 storage ACK 回来，一下推进：

```
VDL
5000 ─────────────→ 5012
```

那么一次 frontier 推进就可以让：

```
A
B
C
D
```

全部满足 durability。

你可以把它理解成一种非常自然的：

```
group commit
```

而且 worker threads 不用同步等待。

# 十、非常重要：VDL ≠ “这些事务全都 commit 了”

这个概念特别容易混淆。

```
VDL
```

表示：

> redo log 到这里已经是 storage-safe 的。

但它并不意味着：

> redo 中涉及的所有 user transaction 都已经提交。

例如：

```
Tx A:

UPDATE ...
UPDATE ...

还没 COMMIT
```

它产生的 redo 也可能已经 durable：

```
LSN <= VDL
```

但是事务仍然：

```
uncommitted
```

所以一定要把两个维度分开：

```
Storage durability
        ↓
       VDL

Transaction visibility
        ↓
MySQL transaction / lock / undo / MVCC
```

Aurora 并没有把 MySQL transaction semantics 搬到 storage layer。

论文明确说：

> concurrency control 仍然像传统 MySQL 一样在 database engine 中执行。

---

# 十一、Read：为什么正常读不需要 read quorum？

这里体现了 Aurora 一个很重要的设计思想：

> **writer 知道 storage 当前的进度。**

假设当前：

```
VDL = 8000
```

发生 cache miss。

Aurora 给这个读取建立：

```
read-point = 8000
```

然后看看 storage nodes 的 SCL：

```
storage A: SCL = 8050
storage B: SCL = 7990
storage C: SCL = 8100
```

那么：

```
A 可以读
B 不可以
C 可以读
```

因为：

```
SCL >= read-point
```

意味着这个节点已经拥有重建：

```
page@LSN8000
```

所需的日志。

于是：

```
Database
   │
   └──── READ page@8000 ───→ storage A
```

一次 read 就够了。

不需要：

```
read A
read B
read C
compare
quorum
```

所以：

> **正常路径 single-copy read。**

只有 crash 后 writer 丢失这些 runtime knowledge，才需要 quorum read。

这是非常重要的一点。

---

# 十二、这实际上是在“花内存状态换正常路径性能”

正常运行时 writer 在内存里知道：

```
每个 PG
每个 storage replica
SCL 到哪里

VDL 到哪里

哪些 commit 正在等

哪些 read 正在进行
```

因此它可以直接说：

```
这个 storage node 可以读。
```

而不用每次：

```
quorum read
```

代价是什么？

一旦 writer crash：

```
这些 runtime state 全没了
```

于是恢复时：

```
重新用 quorum 把它算出来
```

这是 Aurora 很典型的设计哲学：

> **把复杂度从正常路径搬到 recovery path。**

因为：

```
normal requests >> crashes
```

所以值得。

---

# 十三、Read Point 又是什么？

假设：

```
VDL = 1000
```

read 开始：

```
read-point = 1000
```

读到一半：

```
VDL → 1100
```

原来的 read 仍然可能需要：

```
page@1000
```

所以 storage 不能因为 VDL 到 1100，就立即把：

```
1000 之前所有版本
```

全删掉。

否则老 reader 怎么办？

于是产生了下一条水位线：

```
PGMRPL
```

---

# 十四、PGMRPL 是 GC Low Watermark

假设有三个 reader：

```
Reader A: read point = 1000
Reader B: read point = 1200
Reader C: read point = 1300
```

那么：

```
Min Read Point = 1000
```

这意味着：

```
没有任何 reader
会再要求 < 1000 的页面版本
```

如果还有 read replicas，就把 writer 和所有 read replica 的 active read points 一起考虑。

最后得到：

```
PGMRPL
Protection Group Min Read Point LSN
```

可以把它理解成：

```
oldest active snapshot
```

和 MVCC 的 low-water mark 非常像。

于是 storage 可以做：

```
old redo logs
     │
     ▼
coalesce / materialize
     │
     ▼
page
     │
     ▼
GC old logs
```

只要：

```
LSN < PGMRPL
```

这些历史就再没有 reader 需要了。

所以你可以记：

```
VDL
│
└─ 决定：
   哪些东西已经 durable

PGMRPL
│
└─ 决定：
   哪些旧东西已经没人需要，可以 GC
```

这是两个完全不同方向的 frontier。

---

# 十五、这里还有一个特别容易混淆的“Replica”

结合你上一轮的问题，这里一定要再次分清楚：

```
Aurora 的 replica 有两种完全不同的东西
```

第一种是：

```
Storage replicas
```

也就是：

```
一个 PG
     │
     ├─ copy 1
     ├─ copy 2
     ├─ copy 3
     ├─ copy 4
     ├─ copy 5
     └─ copy 6
```

这是负责：

```
durability
fault tolerance
quorum
```

的。

第二种：

```
Aurora Read Replica
```

是完整的：

```
MySQL/Aurora DB compute instance
```

最多可以多个 reader：

```
            Shared Aurora Storage
                    ▲
       ┌────────────┼────────────┐
       │            │            │
     Writer       Reader 1     Reader 2
    compute       compute      compute
```

它们不是那「6 份 storage copy」。

这是两个层次。

# 十六、既然 Reader 都共享 Storage，为什么还要把 redo 发给 Reader？

这是一个很好的问题。

理论上 reader 完全可以：

```
每次 cache miss
    ↓
从共享 storage 读
```

但如果 reader buffer cache 中已经有 page：

```
page X
```

writer 修改了：

```
page X
```

如果完全不通知 reader：

```
reader cache
```

就变旧了。

Aurora 的解决办法：

```
Writer
   │
   ├── redo → storage
   │
   └── redo → read replica
```

read replica 收到：

```
redo record
```

检查：

```
这个 page 在我的 buffer cache 吗？
```

如果在：

```
apply redo
```

如果不在：

```
直接丢掉
```

为什么可以丢？

因为以后真的要读：

```
cache miss
   ↓
storage
```

storage 可以根据 redo 重建最新 page。

所以 read replica 不需要：

```
保存一套自己的 data files
```

---

# 十七、Reader 为什么不能直接应用 writer 发来的所有 redo？

因为 writer 的日志流可能已经跑到：

```
LSN 10050
```

但是：

```
VDL = 10000
```

意味着：

```
10001 ~ 10050
```

还不属于 storage 保证可以保留下来的 durable prefix。

如果 reader 提前应用：

```
LSN 10030
```

然后 writer crash，recovery 最终决定：

```
VDL = 10000
```

那么 10001~10030 必须被 truncate。

Reader 就看到了一段：

```
未来后来被撤销的数据
```

所以 reader 有两个规则。

最重要的是：

```
apply redo only if:

LSN <= VDL
```

并且一个 MTR：

```
全部一起 apply
```

而不是：

```
apply 一半
```

因此：

```
Reader state
```

始终对应某个合法、durable 的 Aurora state。

# 十八、现在终于可以理解 Crash Recovery 了

传统 MySQL / ARIES 风格恢复大致是：

```
disk page
+
WAL
+
checkpoint
```

crash 后：

```
找到 checkpoint
      ↓
scan WAL
      ↓
REDO
      ↓
UNDO
      ↓
database ready
```

问题是：

```
REDO
```

可能非常多。

如果数据库写入量巨大：

```
crash recovery
```

可能很慢。

# 十九、为什么 Aurora 几乎不用做巨量前台 REDO？

因为 Aurora 已经让 storage node：

```
一直在 apply redo
```

不是等 crash 才：

```
redo page
```

而是：

```
正常运行
    ↓
storage continuously
    ↓
append redo
    ↓
materialize page
    ↓
compact log
```

也就是说传统数据库：

```
              crash
                │
                ▼
        大规模 foreground REDO
```

Aurora：

```
运行过程中
   │
   ▼
background distributed REDO
   │
   ▼
storage pages continuously advance
```

所以 crash 后主要工作不再是：

> “把几 GB WAL 全 replay 一遍。”

而是：

> “找出到底哪个 LSN 才是安全边界。”

这就是 Aurora recovery 快的根本原因。

# 二十、Crash 后首先丢失了什么？

storage 没有丢。

丢的是 writer 内存里的：

```
SCL knowledge
current VDL
pending commits
read state
transaction runtime state
...
```

所以新的 writer 必须重新问：

```
storage 现在到底是什么状态？
```

这时候才需要：

```
read quorum
```

例如经典 Aurora 6-copy 模型中：

```
write quorum = 4
read quorum  = 3
```

为什么 3 能发现所有达到 4-copy quorum 的 write？

因为：

```
4 + 3 > 6
```

任何 4 个节点集合和任何 3 个节点集合：

```
至少相交 1 个节点
```

所以：

```
一个真正达到 write quorum 的记录
```

不可能完全避开 recovery 的 read quorum。

---

# 二十一、Recovery 真正是在寻找什么？

对每个 PG 收集 quorum 信息以后，可以重新推导：

```
VCL
```

例如发现：

```
所有必要 redo
连续完整到 1007
```

于是：

```
VCL = 1007
```

然后看看 CPL：

```
900
1000
1100
```

所以：

```
VDL = 1000
```

于是执行：

```
truncate:

LSN > 1000
```

也就是：

```
         keep
<-----------------
... 900 ... 1000 | 1001 ... 1007 ...
                  ↑
                 VDL

                  ------------------>
                       truncate
```

即使：

```
1001~1007
```

物理上存在，也不要。

因为：

> 它们不能组成一个可以保证一致的完整前缀。

---

# 二十二、为什么 LAL 在 recovery 里还有第二个重要作用？

还记得：

```
LSN <= VDL + 10M
```

吗？

正常运行时它是：

```
backpressure
```

但 recovery 时它还有另一个好处。

假设 crash 前：

```
VDL = 1,000,000
```

那么 writer 最多可能创建：

```
11,000,000
```

不会有：

```
LSN 500,000,000
```

藏在某个 storage node 上。

所以恢复系统知道：

```
“可能存在的 tail 最大到哪里”
```

于是可以写一个：

```
truncate range

VDL+1 ... upper-bound
```

把旧 epoch 的所有 speculative tail 全部废掉。

所以 LAL 同时解决：

```
normal path:
backpressure

recovery path:
bound unknown tail
```

这是一个很漂亮的设计。

---

# 二十三、为什么 truncate 还要 epoch？

想象：

```
Recovery 1
```

做到一半 crash。

然后：

```
Recovery 2
```

又开始。

甚至可能有旧 writer 的消息延迟到达。

如果 truncate 只是简单说：

```
delete > 1000
```

storage 很难判断：

```
这是新 recovery 的命令？
还是旧 recovery 的命令？
```

所以 truncation 带：

```
epoch
```

概念上：

```
epoch 15:
truncate > 1000
```

新恢复：

```
epoch 16:
...
```

这样旧时代的操作不能把新时代的状态搞乱。

# 二十四、Recovery 为什么还有 UNDO？

这里非常重要：

> Aurora 只是把 **REDO recovery** 大幅搬到了 storage。

并没有消灭：

```
UNDO
```

例如 crash 时：

```
BEGIN
UPDATE A
UPDATE B
      ← crash
```

这些 UPDATE 的 redo 可能已经：

```
LSN <= VDL
```

所以 storage page 里可能已经包含这些修改。

但事务：

```
没有 COMMIT
```

因此 database engine 必须执行：

```
UNDO
```

把它撤销。

所以 recovery 实际上分两层：

```
Layer 1：Storage recovery

找到 VCL
   ↓
找到 VDL
   ↓
truncate invalid tail
   ↓
Volume 结构一致


Layer 2：Transaction recovery

找到 crash 时的 in-flight transactions
   ↓
undo
   ↓
恢复 SQL transaction semantics
```

这两个千万不要混在一起。

---

# 二十五、最妙的地方：Aurora 可以先上线，再慢慢 Undo

传统 crash recovery 往往：

```
REDO
↓
UNDO
↓
open database
```

Aurora 因为 storage recovery 很快完成：

```
establish VDL
truncate invalid tail
```

数据库就已经有一个结构一致的 Volume。

然后：

```
UNDO recovery
```

可以在线继续。

这也是恢复速度快的重要原因。

# 二十六、把这一节压缩成 5 条 invariant

如果你以后面试或者复习，我建议真正记住下面这几个 invariant，而不是背几十个名词：

1. **Commit invariant**

```
Client can receive COMMIT ACK
only if

commitLSN <= VDL
```

2. **Replica invariant**

```
Read replica only applies

LSN <= VDL

and applies one MTR atomically
```

3. **Read invariant**

```
readPoint = current VDL

choose storage segment with

SCL >= readPoint
```

所以正常读不需要 quorum。

4. **Recovery invariant**

```
VDL = highest CPL <= VCL

everything > VDL
must be truncated
```

5. **Bounded-ahead invariant**

```
allocatedLSN <= VDL + LAL
```

所以 writer 永远不能无限跑在 storage 前面。

这五条几乎就是整个 Section 4。

# 二十七、最后把所有 frontier 放在一张图里

假设：

```
LSN →

1000          1100          1200          1300
 │             │             │             │
 ────────────────────────────────────────────>
```

storage 当前状态可能是：

```
某 segment:

SCL = 1270
                    ↑
       本 segment 完整到这里
```

整个 Volume：

```
VCL = 1247
                 ↑
       volume 物理完整到这里
```

但最近合法 CPL 是：

```
CPL = 1230
               ↑
```

所以：

```
VDL = 1230
```

当前读：

```
Reader A = 1100
Reader B = 1170
Reader C = 1210
```

因此：

```
PGMRPL = 1100
```

整体：

```
             GC frontier
                  ↓
                1100

                                   durable frontier
                                          ↓
                                         1230

                                      complete frontier
                                             ↓
                                            1247

segment completeness
                                                 ↓
                                                1270


───────|────────────────────────────|────|──────|────→ LSN
      1100                         1230 1247   1270
     PGMRPL                        VDL  VCL    SCL
```

你可以这样记：

```
PGMRPL
“过去还能删到哪里？”

VDL
“现在能承诺到哪里？”

VCL
“物理上完整到哪里？”

SCL
“这个具体 storage replica 完整到哪里？”
```

这几个 frontier 一起构成了 Aurora 的核心运行状态。

## 一个值得注意的论文细节：4.2.3 的 page LSN 不等式

你贴的原文确实写的是：

> eviction 时 `page LSN >= VDL`

原始 SIGMOD 论文也是这样写的。[College of Science](https://www.cs.usfca.edu/~mmalensek/cs677/schedule/papers/verbitski2017aurora.pdf?utm_source=chatgpt.com)

但这句话和紧随其后的解释存在明显张力：如果 `page LSN` 表示该页**最后一次修改的 LSN**，那么通常直观上应该是：

```
pageLSN <= VDL
```

才意味着该页的所有修改都已经进入 durable prefix，此时丢掉缓存页，以后从 storage 按 VDL 重建不会丢失更新。多份技术阅读笔记也把原文的 `>=` 视为很可能的笔误，并按 `<=` 来解释。[Flabby](https://flabby.github.io/distributed/2018/12/13/Aurora?utm_source=chatgpt.com)

所以你学习这一段时，我建议按：

```
pageLSN <= VDL
        ↓
这个 page 的最新修改已经 durable
        ↓
可以安全 evict
```

来建立 mental model，而不要让原文这个不等式把整个逻辑带乱。

如果把 Section 4 再压缩成一句话，就是：

> **Aurora 把分布式数据库的一致性和恢复问题，很大程度上转换成了“维护一个有序 redo log，并让 SCL → VCL → VDL 等水位线持续向右推进”；正常路径依靠 writer 保存的 transient state 做单副本读和异步提交，crash 后再通过 quorum 重建这些水位线，并把非安全 tail 截掉。**
