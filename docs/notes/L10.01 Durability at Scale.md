这一节 **“Durability at Scale”** 的核心问题其实可以浓缩成一句话：

> Aurora 不是单纯想做到“磁盘坏一块数据不丢”，而是要做到：**在成千上万台机器持续有小故障的情况下，即使再叠加一次整个 AZ 故障，数据库仍然尽可能可读、可写，而且还能快速恢复。**

这也是为什么 Aurora 同时用了两个设计：

**6 副本 + quorum → 扛住故障**  
**10GB segment → 极大降低修复时间 MTTR**

两者组合起来，才是这一节真正想讲的东西。

---

# 1. 为什么先把 Compute 和 Storage 分开？

传统数据库看起来像：

```
EC2 / DB Instance
│
├── MySQL/PostgreSQL
│
└── Local / attached storage
```

问题是：

```
Compute 生命周期 ≠ Data 生命周期
```

数据库 instance 经常会：

- crash
- reboot
- resize
- failover
- 被客户删除
- 被替换

但数据不能因为 instance 消失就消失。

因此 Aurora 把它拆成：

```
          Compute
        DB Instance
             │
             │ network
             ▼
      Distributed Storage
```

这样 DB instance 可以随时换掉：

```
DB1 crash
   ↓
DB2 接管
   ↓
继续访问同一个 storage volume
```

这其实是 Aurora 架构中非常重要的一步：

> **compute 是 disposable 的，storage 才是 durable state。**

你熟悉 Kubernetes 的话，可以类比：

```
Pod
  ↓
可以随时死

Persistent storage
  ↓
生命周期独立
```

只不过 Aurora 把这个思想推到了数据库存储引擎层面。

---

# 2. Storage 自己也会坏，所以必须复制

把 storage 独立出来并不能解决所有问题。

因为：

```
storage node 会坏
SSD 会坏
rack 会坏
switch 会坏
network path 会坏
整个 AZ 也会坏
```

在超大规模基础设施中，一个很重要的思维变化是：

> “故障”不是异常事件，而是持续存在的 background noise。

比如假设 AWS 有：

```
100,000 块磁盘
```

即使每一块磁盘可靠性都非常高：

```
每天仍然可能有若干磁盘坏掉
```

所以在任何一个时刻，都可能存在：

```
disk A 正在 repair
disk B 网络异常
node C reboot
disk D degraded
...
```

这叫：

```
background failure
```

Aurora 的设计不能假设：

> “平时所有节点都是好的，突然某个 AZ 才坏。”

现实更可能是：

```
已经有一些零星故障
+
突然一个 AZ 掉了
```

这正是这篇论文这里关注的问题。

---

# 3. 最简单的复制方案：3 replicas

最容易想到：

```
          Region

AZ-A          AZ-B          AZ-C
 R1            R2            R3
```

一个数据块保存 3 份。

使用 quorum：

```
V = 3

Write quorum:
Vw = 2

Read quorum:
Vr = 2
```

即：

```
write: 2 / 3 成功即可
read:  2 / 3 成功即可
```

这是非常经典的：

```
2/3 quorum
```

---

# 4. 为什么 quorum 要满足这两个公式？

论文给了两个条件。

## 条件一

```
Vr + Vw > V
```

对于：

```
V  = 3
Vr = 2
Vw = 2
```

有：

```
2 + 2 > 3
```

为什么？

因为这样：

> 任何 read quorum 和上一次 write quorum 一定至少有一个节点重叠。

例如 write 写到了：

```
R1
R2
```

read 读取：

```
R2
R3
```

交集：

```
R2
```

所以 read 至少能够碰到一个包含最新数据的 replica。

图：

```
Write:

R1 ✓
R2 ✓
R3

Read:

R1
R2 ✓
R3 ✓

intersection = R2
```

---

# 5. 第二个条件为什么是 Vw > V/2？

还要求：

```
Vw > V / 2
```

也就是 write quorum 必须是 majority。

原因是防止两个 write quorum 完全不重叠。

例如如果：

```
V = 4
Vw = 2
```

可能出现：

```
Write A:

R1
R2

Write B:

R3
R4
```

两个 write 完全没有 overlap。

于是：

```
R1 R2 → value=A
R3 R4 → value=B
```

系统就出现了冲突。

所以要：

```
Vw > V/2
```

这样任何两个 write quorum 都必然相交。

---

# 6. 那么 3 replicas / 2 quorum 有什么问题？

乍看很好：

```
AZ-A      AZ-B      AZ-C

 R1        R2        R3
```

如果一个 AZ 挂：

```
AZ-C ×

R1
R2
```

还剩 2 个：

```
write 需要 2
read 需要 2
```

似乎刚好能工作。

但 Aurora 认为：

> **这不够。**

原因就是：

# correlated failures

也就是：

**相关故障。**

---

# 7. 什么叫 correlated failure？

单个 SSD 坏通常可以认为是：

```
independent failure
```

例如：

```
AZ-A disk1 坏
```

跟：

```
AZ-B disk2 坏
```

通常没有关系。

但是：

```
整个 AZ-C 断电
```

就不是：

```
10000 个独立磁盘同时随机坏
```

而是：

```
一个事件
      ↓
整个 AZ 内大量机器一起不可用
```

也就是：

```
correlated failure
```

典型原因：

```
power failure
network failure
flood
software deployment
switch failure
AZ control plane issue
```

---

# 8. 关键问题：AZ 故障可能发生在“已有小故障”的时候

假设还是：

```
AZ-A      AZ-B      AZ-C

 R1        R2        R3
```

这时：

```
R1 正在 repair
```

状态：

```
AZ-A      AZ-B      AZ-C

 R1 ×      R2 ✓      R3 ✓
```

现在突然：

```
AZ-C 整个挂掉
```

结果：

```
AZ-A      AZ-B      AZ-C

 R1 ×      R2 ✓      R3 ×
```

只剩：

```
1 replica
```

但是：

```
read quorum = 2
write quorum = 2
```

于是：

```
read ×
write ×
```

数据库不可用了。

这就是论文所说：

> background noise failure + correlated AZ failure

---

# 9. 所以 Aurora 的目标不是“容忍 1 个故障”

Aurora 定的目标更强。

论文明确给了两个目标。

## durability 目标

可以：

```
lose one AZ
+
lose one additional node
```

即：

```
AZ + 1
```

而不丢数据。

---

## write availability 目标

即使：

```
整个 AZ 挂掉
```

仍然可以继续写。

所以他们不能使用：

```
3 replicas
```

最终选择：

# 6 replicas

---

# 10. Aurora 的 6-copy layout

Aurora 将每份数据复制 6 份：

```
                    Region

          AZ-A       AZ-B       AZ-C

          A1          B1          C1
          A2          B2          C2
```

也就是：

```
2 copies / AZ
×
3 AZ
=
6 copies
```

所以：

```
V = 6
```

quorum 为：

```
Vw = 4
Vr = 3
```

即：

```
write quorum = 4/6
read quorum  = 3/6
```

---

# 11. 为什么是 4 write quorum？

检查 quorum 条件：

```
Vw > V/2
```

也就是：

```
4 > 3
```

成立。

而：

```
Vr + Vw > V
```

即：

```
3 + 4 > 6
```

成立。

所以：

```
V = 6
Vw = 4
Vr = 3
```

满足经典 quorum intersection。

---

# 12. 为什么 AZ 故障后还能写？

假设 AZ-C 整体挂：

```
AZ-A        AZ-B        AZ-C

A1 ✓        B1 ✓        C1 ×
A2 ✓        B2 ✓        C2 ×
```

剩：

```
4 replicas
```

而：

```
write quorum = 4
```

所以：

```
仍然可以写
```

这就是论文说：

> lose an entire AZ without impacting the ability to write data

---

# 13. 为什么可以容忍 AZ + 1 还能读？

假设：

```
AZ-C 整个挂掉

C1 ×
C2 ×
```

然后 AZ-A 又坏了一个：

```
A1 ×
```

剩：

```
A2
B1
B2
```

一共：

```
3 replicas
```

而：

```
read quorum = 3
```

所以仍然：

```
read ✓
```

状态：

```
AZ-A        AZ-B        AZ-C

A1 ×        B1 ✓        C1 ×
A2 ✓        B2 ✓        C2 ×

remaining = 3
```

因此：

```
AZ + 1
```

仍然可以维持 read quorum。

---

# 14. 但为什么 AZ+1 时不能继续写？

因为只剩：

```
3
```

而 write quorum 要：

```
4
```

所以：

```
write ×
```

这其实是一个非常重要的 distinction：

```
AZ failure
    ↓
4 copies remain
    ↓
read ✓
write ✓


AZ + 1 failure
    ↓
3 copies remain
    ↓
read ✓
write ×
```

但是只要还能 read：

```
我们就还能知道有效的数据
```

然后可以：

```
复制一个新的 replica
```

恢复：

```
3 → 4
```

于是：

```
write quorum 恢复
```

这就是论文这句话：

> Ensuring read quorum enables us to rebuild write quorum by adding additional replica copies.

---

# 15. 到这里还有一个大问题：6 replicas 就足够安全吗？

还不够。

因为你必须考虑：

```
一个 replica 已经坏了
```

到：

```
它 repair 完成
```

之间存在一个时间窗口。

叫：

# vulnerability window

假设：

```
disk failure
    ↓
等待 repair
    ↓
repair 1 hour
```

那么这一个小时里：

```
系统少了一份 replica
```

如果这个窗口里：

```
又发生一个 failure
+
AZ failure
```

可能就突破 quorum。

所以可靠性不仅取决于：

```
MTTF
```

还取决于：

```
MTTR
```

---

# 16. MTTF 和 MTTR

两个重要概念：

```
MTTF
Mean Time To Failure
```

平均多久发生一次 failure。

以及：

```
MTTR
Mean Time To Repair
```

坏了之后多久恢复。

数据库系统常常不能无限提高：

```
MTTF
```

因为：

```
SSD 总会坏
machine 总会坏
network 总会坏
```

于是 Aurora 换了一个思路：

> 既然我很难让硬件永远不坏，那我就让它坏了之后极快修复。

也就是重点降低：

```
MTTR
```

---

# 17. 这就是为什么 Aurora 要做 Segmented Storage

如果一个 Aurora volume 是：

```
10 TB
```

某台机器存着整个 10TB replica。

机器坏了：

```
copy 10TB
```

可能需要：

```
hours
```

于是 vulnerability window 很大。

Aurora 不这么做。

它把 database volume 切成：

```
10 GB segment
```

论文中的设计是：

```
10GB
```

每一个 segment 独立复制 6 份。

---

# 18. Protection Group 是什么？

这是你前面问过的概念。

假设逻辑数据：

```
segment #123
size = 10GB
```

Aurora 为它制造：

```
6 copies
```

例如：

```
AZ-A
  seg123-A1
  seg123-A2

AZ-B
  seg123-B1
  seg123-B2

AZ-C
  seg123-C1
  seg123-C2
```

这 6 个 copy 合起来叫：

# Protection Group

简称：

```
PG
```

因此：

```
PG = 6 × 10GB replica segments
```

但这里非常容易搞混：

逻辑数据量只有：

```
10GB
```

物理复制之后：

```
60GB raw replica storage
```

所以：

```
一个 PG
=
一个 10GB logical range
+
6 个 replica
```

---

# 19. Aurora Volume 又是什么？

Aurora volume 就是：

```
PG1
+
PG2
+
PG3
+
PG4
+
...
```

逻辑上连接起来。

比如：

```
Aurora Volume = 100GB
```

那么大概可以理解为：

```
PG1  0-10GB
PG2 10-20GB
PG3 20-30GB
...
PG10 90-100GB
```

每个 PG：

```
6 replicas
```

所以整体关系是：

```
Aurora Volume
│
├── PG1
│   ├── replica A1
│   ├── replica A2
│   ├── replica B1
│   ├── replica B2
│   ├── replica C1
│   └── replica C2
│
├── PG2
│   ├── 6 replicas
│
├── PG3
│   ├── 6 replicas
│
└── ...
```

所以你可以直接记：

```
Volume
  ↓
many Protection Groups
  ↓
each PG = one 10GB logical segment × 6 replicas
```

# 20. 为什么 10GB segment 能极大降低 MTTR？

假设坏的是：

```
segment X
```

Aurora 不需要：

```
重建整个 1TB / 10TB database
```

只需要：

```
repair 10GB
```

论文中说：

```
10 Gbps network
```

大约：

```
10GB ≈ 80Gb

80Gb / 10Gbps ≈ 8 seconds
```

考虑 overhead，大概：

```
~10 seconds
```

因此：

```
MTTR ≈ 10 seconds
```

而不是：

```
hours
```

这对 durability 有极大影响。

---

# 21. 这实际上是个概率问题

Aurora 真正在控制的是：

> 在 repair window 内，再发生足以破坏 quorum 的其他故障的概率。

如果：

```
repair = 10 hours
```

那么另一个 failure 落入这个窗口的概率相对大。

如果：

```
repair = 10 seconds
```

那么窗口就极小。

可以粗略理解：

```
risk ∝ failure rate × MTTR
```

所以：

```
MTTR ↓↓↓
```

会显著降低：

```
multiple overlapping failures
```

发生的概率。

这就是论文这句话最核心的意思：

> It is difficult, past a point, to reduce MTTF...  
> We instead focus on reducing MTTR.

这是非常经典的 SRE / distributed storage 思维。

---

# 22. 为什么 segment 本身也是 failure domain？

论文说：

> Segments are now our unit of independent background noise failure and repair.

意思是：

Aurora 不再把：

```
整个 DB
```

当成 repair unit。

而是：

```
10GB segment
```

例如某个 storage node 坏了：

```
node X
│
├── PG31 replica
├── PG42 replica
├── PG85 replica
└── PG102 replica
```

Aurora 可以分别把它们：

```
PG31 → machine A
PG42 → machine B
PG85 → machine C
PG102 → machine D
```

并行重建。

所以 recovery 变成：

```
many tiny repair jobs
```

而不是：

```
one giant disk rebuild
```

这和传统 RAID rebuild 是很大的区别。

# 23. Section 2.3 的重点：Fault tolerance 还能带来 Operational Benefits

这是这一节很精彩的地方。

Aurora 发现：

> 如果一个系统能够容忍真正的故障，那么你也可以故意制造“短暂故障”来做维护。

例如一个 storage node：

```
node X
```

太热：

```
hot disk
```

可以直接：

```
mark segment bad
        ↓
复制到 colder node
```

不需要数据库停机。

---

# 24. OS patch 也是同样逻辑

比如：

```
storage node reboot
```

传统系统可能觉得：

```
危险！
```

Aurora：

```
只是短暂少一个 replica
```

而系统本来设计就能：

```
lose 1 replica
lose 2 replicas
甚至 lose AZ
```

所以 reboot 一个 node 没什么。

---

# 25. Software upgrade 也是这样

Aurora 可以：

```
AZ-A upgrade
    ↓
AZ-B upgrade
    ↓
AZ-C upgrade
```

但保证：

```
同一个 PG
不会同时 patch 太多 replicas
```

论文写的是：

> no more than one member of a PG is being patched simultaneously

也就是例如：

```
PG123

A1 patching
A2 ✓
B1 ✓
B2 ✓
C1 ✓
C2 ✓
```

不会出现：

```
A1 patch
B1 patch
C1 patch
```

把 quorum 人为打掉。

这本质上就是你很熟悉的：

```
PodDisruptionBudget
```

思想。

可以类比 Kubernetes：

```
replicas = 6

maxUnavailable = 1
```

Aurora 在 storage fleet 层面实现类似的 operational invariant。

# 28. 为什么这比“6 副本很安全”更深一层

这篇 Aurora paper 真正想强调的不是：

> 我们复制了 6 份，所以 durability 很高。

而是：

> **Durability 是 replication factor、failure correlation、quorum geometry 和 MTTR 共同决定的。**

也就是：

```
Durability
≠
只看 replica count
```

而应该看：

```
Durability
≈
Replication
×
Failure-domain separation
×
Quorum properties
×
Repair speed
```

例如：

```
6 replicas
```

但全放一个 rack：

```
rack failure
→ 全没
```

没意义。

又比如：

```
6 replicas across AZ
```

但是 repair 一次要：

```
24 hours
```

那么多个 overlapping failures 的概率还是会上升。

所以真正优秀的分布式存储设计，会同时设计：

```
placement
quorum
repair unit
repair speed
failure domain
```

# 29. 和后面 Aurora 内容的关系

这一节主要解决的是：

```
Where does data live?
How many copies?
What failures can storage survive?
```

后面论文才会继续回答：

```
write 怎么发送到这 6 个 replicas？

redo log 怎么传播？

什么时候一个 LSN 算 durable？

storage node 怎么知道缺了哪些 log records？

read 时怎么找到正确 page？

crash recovery 怎么做？
```

所以整个 Aurora paper 的思路可以粗略看成：

```
Section 2
Durability topology
        ↓
6 copies / quorum / PG / segments

Section 3+
Write path
        ↓
redo records / LSN

然后
        ↓
durable frontier
        ↓
recovery
        ↓
read path
```

这也是为什么你之前问到的 **LSN / Durable Frontier / Protection Group** 都和这一节直接连起来。

如果你只记住 Section 2 的一句话，可以记：

> **Aurora 用 6-way replication 抵抗 AZ 级 correlated failure，用 10GB segmentation 把 repair 从“大规模重建”变成约秒级的小块重建，从而通过降低 MTTR，把多个故障重叠并导致 quorum 丢失的概率压到极低。**
