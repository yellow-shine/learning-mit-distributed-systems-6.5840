# 11 — 持久化与崩溃恢复：讲了为什么，没做出来

## 1. Problem

进程崩溃和网络分区不是一回事。

```text
分区:   状态还在内存和磁盘里，只是消息过不去
崩溃:   进程没了。重启后，只剩下你写进耐久介质的那些字节
```

若重启后 `currentTerm` 回到 0，这台机器会用旧身份投票或发令。若 `votedFor` 丢了，它可能在同一个 term 再投一次，选出两个 leader。若日志丢了，已提交命令消失，安全直接没了。

## 2. Naive Solution

- 全放内存。重启当新节点。他的学生碰到过：不持久化的话，一崩溃整份状态没了 (D5 2_part038)。
- 在 apply 的时候把状态机倒到磁盘。学生觉得这是自然时刻：已经共识了，正在执行。他不接受这就是 Raft 的持久化点 (D5 2_part038–2_part039)。
- `write()` 进内核缓冲就算持久。掉电仍丢。
- 日志对象只保留最后 100 条，数组下标当 index。这是他在 Project 4 卡住时冒出来的想法，他自己叫它可能很可怕 (D2 2_part039)。
- 重启时再插入一条 poison 条目，让空日志的特例消失。学生担心和已有快照冲突 (D3 1_part007)。

## 3. Why It Fails

**只在 apply 时写盘。** 提交点可以领先 apply。崩溃发生在 commit 之后、apply 之前，这条已提交命令不在磁盘上。即使你写的是状态机，也没写 `currentTerm` 和 `votedFor`。下次选举会用过期的任期投票。

**只写日志、不写投票。**

```text
S2 currentTerm=4，投给 S1，回复已经发出
S2 崩溃，votedFor 丢了，currentTerm 也丢了
S2 重启，又在 term 4 投给 S3
S1 和 S3 都可能凑够多数
```

【Raft 论文补充】这是“先落盘，再回复”的原因。课上没有走这个剧本。不要把它写成他演示过。

**write 没有 fsync。** 他的说法是：论文要的是物理介质上的数据，掉电能活，不是 RAM (D5 2_part038–2_part039)。怎么做，他说是个可怕的问题，这周没谈。

**用数组尾部冒充日志。** 截断之后，`log[i]` 的 i 不再是 Raft index。`len` 更不是 lastLogIndex。他在 D2 已经警告过这两个坑，尽管快照没做 (D2 2_part040)。

## 4. Raft Solution

【Raft 论文补充】Figure 2 的持久状态，崩溃后必须还在：

```text
currentTerm
votedFor
log[]
```

易失，可以重算或重新爬：

```text
commitIndex      重启后常从 0 或从快照的 lastIncludedIndex 重新前进
lastApplied      同上，但要避免把已应用命令再执行一次
nextIndex[]      变成 leader 时重建
matchIndex[]     变成 leader 时重建
```

易失不等于“丢了也无所谓”。`lastApplied` 若回到 0 而状态机还留着旧结果，会重复执行。所以要么状态机和 lastApplied 一起持久，要么应用命令幂等。课上两者都没做完。他只把“日志必须持久、已提交不能变”说成了要求。

投票必须在回复之前落盘。顺序：

```text
决定投给候选人
写入 currentTerm 和 votedFor
确认落盘
然后发送 RequestVote 响应
```

日志追加同样：

```text
把条目写入持久日志
确认落盘
然后对 AppendEntries 回 success
```

否则你回了 success，对方据此提交，你重启后那条不在了。

【课程内容】他实际说的比这少：日志是持久状态；命令进了日志就不该因为崩溃消失；已提交值冻结；怎么写到盘上、写在哪一层，没解决 (D2 1_part005，D5 2_part038)。Roblox 的故障写报告里有持久存储的问题，他记得可能和一次软件升级后的行为变化有关，让 Raft 出问题或性能出问题。他说“I think”，要求课后去读，不要把细节当成他已核实的结论 (D5 2_part039)。

### 快照：为什么本周不做

【课程内容】D3 1_part004–1_part007，D5 2_part039 “not now”。

日志不能无限长。做法是对应用做快照，丢掉快照点之前的日志。崩溃后加载快照，重放之后的日志。数据库就是这样。

学生的简单方案：大家大致同步，在共同前缀处做一次全局快照，然后忘掉前缀。失败在“大家”。一台机器可以离线几天，其余节点继续前进并截断。回来的机器要的条目，leader 已经没有了。Leader 改发快照。一台快照可能不够，所以是第 7 节 log compaction，不是他最初猜的第 6 节 (D3 1_part005–1_part006)。

还没解决的设计问题，他列了就停：

- 谁发起？是 leader 吗？
- 文件放哪？
- 消失的前缀怎么管？
- 快照时 KV 能不能继续变？他认为变就是灾难 (D3 1_part006–1_part007)。
- Roblox 面板上 apply 约 30ms，raft snapshot 19.8 秒。他不知道那 19.8 秒是写入耗时还是间隔，也不知道期间 Raft 在干什么。学生猜系统可以继续跑，19 秒不是一道屏障。没有结论 (D3 1_part006)。

他从没在一个课程周里把快照做成功，这周也不做。日志 API 看起来怪，可能是因为他在想截断。忽略那部分，先把复制做对 (D3 1_part007)。

空日志用初始条目绕开，是脚手架。重启不应再插入 poison。持久化本该留下第一条 (D3 1_part007)。

### 成员变更

【课程内容】第 6 节 joint consensus。他读过一两次，搞不清怎么写。理解停留在：从 3 台换成 5 台时，有一段时间两套配置同时跑，达成联合共识后再退役旧配置 (D5 2_part039，D2 1_part002)。TLA 规格里他没看到 reconfig。学生提议用快照换一台机器、IP 不变。他说不知道，留成周末作业。

【Raft 论文补充】不能在旧配置和新配置上各选出一个 leader。Joint consensus 是过渡期要求两边的多数都同意。单节点替换若做成“停机、拷贝、启动”，在拷贝期间集群少一台，可能失去多数。这不是课上的结论。

## 5. Example

三节点，只展示“投票先落盘”这一个论文剧本。标成补充，避免和课堂演示混淆。

```text
【Raft 论文补充】

S1 发起 term=2
S2 决定投票，先把 (term=2, votedFor=S1) 写入磁盘，再回复赞成
S2 在回复之后崩溃

重启 S2，读回 term=2, votedFor=S1
S3 来要票，term 仍是 2
S2 拒绝

若 S2 在写盘前就回复并崩溃:
  重启后 votedFor 为空
  S3 可能拿到 S2 的票
  S1 也可能已经拿到了包括 S2 在内的多数
  term 2 两个 leader
```

崩溃恢复和分区的对比：

```text
分区恢复:  旧 leader 内存里的 term 还在，看到更高 term 就下台
崩溃恢复:  若 term 没写盘，它会从旧 term 开始，主动发起一场不该存在的选举
```

## 6. Invariant

- 回复任何 RPC 之前，持久状态已经在耐久介质上。否则回复里承诺的事实可能随崩溃消失。
- 重启后 `currentTerm` 不小于崩溃前最后一次落盘的 term。
- 重启后日志前缀包含崩溃前已向别人确认过的条目。
- `commitIndex` 可以比崩溃前小，然后被新的 leaderCommit 或自己的重算抬回去。不能因此重新执行已经对客户端可见、且非幂等的命令。这条在没做快照时很难同时满足，所以课程避而不做。
- 快照的 lastIncludedIndex 之前的日志可以没有，但选举和 AppendEntries 必须能用快照元数据比较“我有多新”。【论文补充】InstallSnapshot。课上没讲 RPC 字段。

## 7. Failure Cases

**崩溃在 fsync 之前。** 对方已经收到 success。你重启后短一截。对方可能已提交。这是安全事故。

**崩溃在 fsync 之后、回复之前。** 对方会重试。你的日志已有该条，prev 匹配，幂等成功。这是允许的。所以落盘必须在回复之前，可以在对方知道之前。

**只恢复了状态机，没恢复日志。** 新命令会写在空日志上，和集群的 index 对不上。他拒绝空日志，就是在躲这个角落的一小部分，不是在解决它。

**快照期间 set 还在跑。** 快照里的字典和日志的截断点不是同一时刻。重放会重复或丢失中间命令。他称为灾难配方 (D3 1_part007)。

若要补最小持久化，【从课程推导】落点应该在 RaftLog 和 RaftLogic 里那些改变持久三元组的函数末尾，而不是在 app.execute 里。Server 不应该是唯一知道该 fsync 的人，否则 logic 的单元测试会承诺一种崩溃后不成立的成功。

【MIT 6.5840 实现补充】Lab 2C 要求 `persist()` / `readPersist()`，在每次改变持久状态后调用，并且重启后通过同一套测试。Lab 2D 才是快照。Beazley 的周里，2C 和 2D 都在范围外。做 lab 时不要把“他没做”理解成“不重要”。2C 的 bug 通常是：回复已经发出，persist 在另一个 goroutine 里还没跑。

## 9. Common Bugs

- apply 时才写盘。
- 写盘和回复并发，用锁锁了逻辑却没等 fsync。
- 只持久化 log，不持久化 term。重启后 term 回退，违反“term 不减”，并可能投出第二票。
- 持久化了 term，没持久化 votedFor。
- 用 pickle 把整个对象图包括 socket 一起存。恢复后 socket 是坏的，逻辑也被绑死。他在编码讨论里提到过 pickle 当消息边界，不是当崩溃镜像 (D2 1_part028)。
- 把 commitIndex 写进磁盘又在重启时信任它，但日志短一截。commitIndex 指向不存在的条目。
- 快照和日志截断不是同一个 index。
- Python `log[-1]` 在恢复代码的 off-by-one 里读到最后一条，把损坏的前缀当成匹配 (D2 2_part041)。

## 10. Course Insight

他想让你区分两种“不在”：机器还在、话送不到；机器的内存没了、只剩磁盘。第一种用多数派和 term 处理，这周写了。第二种要求在说“是”之前把话说进耐久介质，这周只点到为止。

学生觉得写磁盘很直接。他的回答是：直接的是应用的存档直觉，不是 Raft 的持久化。Raft 要保存的是还没执行的日志、任期和投票，而且要挡掉电。再加上快照和成员变更，他明确说超出这一周，第 6 节也超出他当时的把握。

若你的实现重启即丢状态，就不要用它验证“崩溃后已提交命令还在”。那个性质在这门课的代码里还没有被实现，只被断言在内存消息处理的前后。
