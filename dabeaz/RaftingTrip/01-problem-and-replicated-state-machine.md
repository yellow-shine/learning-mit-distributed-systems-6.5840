# 01 — 从单机到复制状态机

## 1. Problem

一台服务器、一个状态，客户端把命令送进去。这不是分布式系统，但这是 Raft 要保护的那个东西。

【课程内容】(D1 1_part002) 应用可以是数据库，也可以是文字处理器。命令按顺序进来，一次执行一条。技术说法是原子的：先跑完这条，再跑下一条。不是所有系统都这样，但这门课只使用这个模型。

然后问四个越来越讨厌的问题：

1. 进程崩溃，内存状态丢了。
2. 周期性快照保不住最后几条命令。
3. 事务日志所在的磁盘也会没。
4. 唯一的备份机器死了之后，你还敢继续提供服务吗？

etcd 演示把第 4 问变成可以看见的超时 (D1 1_part007–1_part008)。

## 2. Naive Solution

自然的一层层补丁，也是他课堂上顺着学生往下走的那条路：

```text
只跑一个进程
  → 每分钟把字典快照到文件
  → 命令先写入日志再执行，崩溃后重放
  → 日志再拷贝到一台备份机
  → 备份挂了就先读、不写，或者“看情况”
```

学生在 KV 作业里已经走到这一步：有人把整个字典存下来再恢复，发现要加锁；有人觉得恢复必须重放快照里的命令，怀疑结构已经错了。他当天没写快照，也没有裁判谁对 (D1 1_part038–1_part039)。

另一个自然方案是客户端自己把 `set x 42` 发给所有服务器。他没有把这个方案在白板上打倒，而是直接规定路径：客户端只跟 leader 说话，leader 把命令放进日志，再发给 follower (D2 1_part001)。

## 3. Why It Fails

**快照不够。** 一分钟一次的备份，最近的命令不在文件里。数据库可以 12 小时做一次快照，中间全靠日志 (D1 1_part002–1_part003)。

**单份日志不够。** 日志是一块硬件。硬盘坏、机房着火，重放的原材料没了。

**一份备份不够。** 备份死了还继续服务，等于回到没有备份。接着主程序也崩溃，那些没写出备份的命令就真的没了 (D1 1_part004)。

**“读好像可以”不够。** 三台 etcd 死两台，GET 也会坐在那里然后超时。Raft 说做什么都要多数派，读不是后门 (D1 1_part008)。

**客户端只认识一台也不够。** 他杀掉客户端唯一知道的那台，另外两台还活着，客户端仍然失败。把三个地址都写进客户端命令之后才工作。学生问：活着的那台不能介绍其他节点吗？他的回答是：你怎么知道那一台是活的？这又回到原来的问题。再加一个注册中心，注册中心死了你还是死，于是注册中心也要 Raft，然后那个 Raft 又要注册中心 (D1 1_part008–1_part009)。

**Follower 一收到就执行也不够。** Follower 彼此不通信，不知道集群里有几份。Leader 执行的时刻，不是 follower 可以执行的时刻 (D2 1_part002–1_part003)。

## 4. Raft Solution

目标用论文 Figure 1 说完 (D1 1_part004–1_part005)：

```text
Client Command
      |
      v
+-------------+
|    Log      |   每台一份，内容要相同
+-------------+
      |
      v
+-------------+
| State Machine |  确定性执行
+-------------+
```

高层次上 Raft 是：一个能从备份恢复、能容忍机器故障的可靠应用。细节后面五天才补上。

他愿意当天列举的故障只有两类，而且他拒绝把清单合上 (D1 1_part005)：

- 机器死了。
- 机器没死，但是不能通信。

性能下降也存在。他说 Raft 里还有很多可怕的事，以后再进。

它被用在什么地方，也是这个问题的一部分。不要在边缘的 web server 上跑 Raft。典型画面是：成千上万台对外的机器，中间有一个很小的注册中心，认证、负载均衡、配置都问它。注册中心死了，公司就死了。所以复制的是注册中心 (D1 1_part005–1_part006)。

他后来反复引用的两个部署：

- Roblox：约 73 小时全站故障；大约 18,000 台服务器、170,000 个容器；Raft 用在大约五台机器的服务注册中心上 (D1 1_part006)。
- Cloudflare：一个三节点 Raft 集群也能把不小的公司打出故障 (D1 1_part009，D4 展开成分区故事)。

集群是 3 或 5，不是几十。学生指出：五台已经比把几百个地址交给客户端要好 (D1 1_part009)。成员变更很可怕，这门课不做 (D2 1_part002)。

## 5. Example

三台 etcd，这是整门课的目的地缩影，不是学生当天要写完的东西。

```text
时间 →

启动 1 台
  put name=Guido, x=42
  get 成功
  杀掉这台
  get 坐一会儿，超时          ← 要避免的事

启动 3 台
  put / get 成功
  杀掉第 2 台
  客户端无感知               ← 1/3 失败仍可工作

杀掉两台
  get 超时                   ← 2/3 失败，多数派没了
  “我只是读” 也不行

重启 3 台，只告诉客户端第 1 台的地址，杀掉第 1 台
  另外两台活着，客户端仍失败  ← 客户端必须预先知道全部端点
  把三个地址都给它，它才能去找 leader
```

对应到他们即将写的 KV：`set` / `get` / `delete`，多客户端。这就是 Figure 1 里的状态机。图里甚至画了 `x=3, y=9` 这种值 (D1 1_part010, 1_part039)。

Figure 1 拆开之后，他们的 KV 服务器已经有了外圈，没有中心 (D1 1_part040–1_part041)：

```text
1. 客户端把命令送到某台服务器          他们已经有 receive
2. 若不是 leader，叫客户端走开          还没有
   若是 leader，命令先进入日志          还没有
   日志复制到“足够多”的机器            还没有
3. 状态机执行                          他们已经有 execute
4. 把结果送回客户端                    他们已经有 send response
```

“足够多”当天不定义。中间被他叫做 magic：命令先被 staged，复制够了才执行。

## 6. Invariant

这一层还没有 term，能说的不变量很少，但都是后面的前提：

- 命令有顺序，一次一条。后面“日志相同 ⇒ 状态相同”依赖确定性。并发改同一个键不是 Raft 要替你排的语义 (D4 才把这个说透)。
- 日志相同，命令序列才相同。
- 没有备份就不要继续提供“不会丢命令”的服务。后面会把“备份还在”收紧成“多数派还在”。
- 客户端只和 leader 说话。Follower 应该拒绝，而不是偷偷执行 (D1 1_part041)。

【从课程推导】为什么复制日志比复制最终状态容易建立一致性模型：

- 状态是命令的函数。日志是函数的输入序列。输入序列一致，加上确定性，输出就一致。
- 最终状态没有“缺了哪一步”的地址。日志有 index。重试、冲突、回退都要一个地址。
- 崩溃恢复是重放，不是猜测内存里的字典是否写到一半。
- 两个副本发散时，你比对的是前缀，不是两份字典的差。字典的差不能告诉你哪条命令是赢家。

他当天没有用这四句话。他用的是：Figure 1 要求相同命令序列，而相同序列来自相同日志。

## 7. Failure Cases

| 事件 | 这一章的结论 | 还不能回答的 |
| --- | --- | --- |
| 单机崩溃 | 快照 + 日志重放，仍可能丢日志盘 | 多副本协议 |
| 备份盘损坏 | 必须有多份日志 | 哪一份为准 |
| 三分区，一台被切开 | 他只说这是要处理的，不是死机的同义词 | 谁继续提交 |
| 客户端只知道一台，那台是 follower 或已死 | 看起来像全站故障 | 发现 leader 的协议，课上最终也没做完 |
| 命令已经进了 leader 内存，还没写日志 | 不应算成功 | 何时回复客户端，D4/D5 |

网络分区和死机从第一天就分开。后面不要把它们写成同一种故障。

## 8. Implementation Notes

【课程内容】Project 1 的分层，是为了让状态机在没有 Raft 时就能测 (D1 1_part024, 1_part038–1_part039)：

```text
KV app
  run_command("set X123") -> response
  无 socket，无线程，无编码
  能在 REPL 里戳

execute_command(bytes) -> bytes
  编码/解码放这里更说得通
  他没定死。换 async 不应被迫改编码，所以也许是第三个对象
  有人说 factory，他开玩笑把 factory / proxy / adapter 赶下桌

Server
  socket 在这里
  取消息，塞给应用，送回响应
```

不要把 socket 和线程放进应用核心。网络层测起来很痛苦：你得起服务器、起客户端。如果外层不可测，他可以忍受；内层必须能在没有网络时调试 (D1 1_part025)。

Project 2 的 traffic light 不是 Raft，但是同一条结构命令 (D1 2_part003–2_part021)：规则是一个不碰 socket 的对象；时间、按钮、颜色输出是控制器的事。他希望 Raft 的 Figure 2 也能这样测。细节在 [12](12-concurrency-and-timers.md) 和 [13](13-code-evolution.md)。

语言不限。Rust 不会允许他在 Python 里走的捷径 (D1 1_part011)。

## 9. Common Bugs

这一章还没有 Raft 代码，坑是问题模型上的：

- 从论文状态机、人人都是 follower 开始写。他明确说这是错的起点。主目标是复制日志，那是论文里最大的一节 (D1 1_part011)。
- 把 Raft 套在边缘 web server 上。
- 认为只读可以绕过多数派。etcd 演示已经否定。
- 用一个注册中心来发现 Raft 集群，然后没发现注册中心自己也是单点。
- 在应用对象里直接做网络编码，又在网络层里直接改 KV。后面换传输时两边一起烂。
- 快照做成“把字典倒出去”，没有想过快照期间应用还在变。D3 他会把这个叫做灾难配方。

## 10. Course Insight

他想让你先相信一件事，再碰任何 RPC：Raft 是一个复制日志的算法，日志喂给一个确定性状态机。选举、term、提交都是为了让“日志相同”在故障下仍然成立，并且不要把没承诺过的成功告诉客户端。

第一天结束时他拒绝指定第一行代码。三个候选起点，都算家庭作业 (D1 2_part040)：

1. 先做能发消息的机器环境。
2. 先做 Figure 1 的命令怎么流过那些盒子。
3. 先把 Figure 2 像红绿灯逻辑那样单独写成可测对象。

第二天他会把这三件事收成一种结构，但仍然不从选举开始。
