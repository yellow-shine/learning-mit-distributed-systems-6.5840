# 16 — 论文、MIT 6.5840、真实系统，以及 Raft 不负责什么

## 论文：Figure 2 是规范，不是摘要

【课程内容】材料在 raft.github.io。他希望大家去过。算法描述主要是第 5 节，但第一天不进第 5 节。Visualizer 在同一站点，课上反复当实验台 (D1 1_part000)。

标题里的 understandable 是相对 Paxos。他同意这个词干活太多 (D2 1_part000)。论文很密，因为会议页数有限。他仍然觉得这篇写得不错。编码和读论文不能同时进行，要先读多遍 (D5 2_part010)。有学生读了三遍仍讲不清 index 和消息里的变量。

他的读法不是逐行翻译。是：Figure 1 当软件结构，Figure 2 当接收规则的字面文本，Figure 6 当选举测试，Figure 7 当日志收敛测试，Figure 8 当“这条 if 为什么存在”。TLA 规格当第三份说明书，不是可运行实现。

【Raft 论文补充】Figure 2 应被当成协议规范。实现时以那一页的状态、两个 RPC、服务器规则为准，而不是以任何教程的中位数或 visualizer 的额外字段为准。Visualizer 多出来的 matchIndex 回复字段可以用，但要知道论文没要求 follower 发送它。

安全性质的名字和依赖见 [10](10-safety-and-liveness.md)。论文 §5.4 的证明比课堂故事严。课堂故事足够知道每条 if 在堵哪个洞，不够代替证明。

## MIT 6.5840

【课程内容】他提到 MIT 的 Raft 课：不要等到截止前一晚才开始，否则会死 (D5 2_part009)。D3 提到一份 MIT 学生指南，强调细节，尤其冲突规则里的 “if” (D3 1_part008)。他没有讲 lab 的 API。

【MIT 6.5840 实现补充】下面的对应是为了做 lab，不是字幕内容。6.5840 的前身是 6.824。Lab 2 通常分成：

| Lab | 你要交的 | 这门课的哪一块 | 课上没有、lab 会打你的 |
| --- | --- | --- | --- |
| 2A | `RequestVote`、选举、`ticker` | D5 的选举和计时器 | tester 的时间很紧；心跳和选举超时的比例；分区期间不能选出两个 leader；必须在超时内稳定 |
| 2B | `Start`、`AppendEntries`、`applyCh`、nextIndex、matchIndex | D3–D4 的复制、提交、apply | 图 8 的 current-term 规则；不可靠 RPC；`Start` 在失去领导权时要返回失败；apply 必须按序送到 channel |
| 2C | `persist` / `readPersist` | D5 只讨论了为什么难 | 每次改持久状态都要在回复前完成；重启后 tester 继续打 |
| 2D | snapshot、`InstallSnapshot`、`CondInstallSnapshot` | D3 讲了为何不做 | 快照和进行中的 apply 的竞态；截断后的 index |
| 3 kvraft | client id、重复检测、线性读 | D4–D5 的 UUID 和 GET 等待区 | 客户端会重试；leader 变更时 in-flight RPC；只读不能破坏线性 |

API 对照：

```text
RequestVote / AppendEntries     课上的两种 RPC，加上响应
ticker                          外层计时器。课上没写死放哪
Start                           客户端把命令交给 leader。不是 leader 要拒绝
applyCh                         他的 lastApplied 循环。lab 要求把已提交命令送出，而不是打印
persist / readPersist           课上未做
nextIndex / matchIndex          D3–D4 的核心。lab 里失败回复可能带冲突索引，优化可选
```

做 lab 时和他的顺序相反：2A 先选举。他的警告仍然有效。选举通过不要推断复制容易。2B 的痛苦才是他称为宇宙中心的那部分。

Lab 额外会打、这门课只点到或没点到的：

- 不可靠 RPC：延迟、重复、乱序。他在 D5 把这些放进假网络菜单，没有 lab 那种自动 tester。
- 并发：goroutine 比他的 Python 线程更容易在持锁时发 RPC。
- 持久化时机。
- 快照与 apply 的交错。
- tester 的时钟不会等你的 `sleep` 调试。
- 选举的角落：同一 term 的重复投票、过期的 RequestVote、候选期间收到 AppendEntries。
- `Start` 的返回值：当前 term 和 index，以及是否是 leader。失去领导权后，客户端必须用新的调用重试，不能假设旧 index 还会执行。

## 真实系统里 Raft 在复制什么

【课程内容】他拒绝把 Raft 放在边缘 web server 上。复制的是关键的小集群：注册中心、认证、负载均衡、配置 (D1 1_part005–1_part006)。

| 系统 | 课上怎么出现 | 它实际让 Raft 复制的东西 |
| --- | --- | --- |
| etcd | D1 演示，D5 用来解释 GET 超时 | 【课程内容】网络上的 KV。 【工程实践补充】Kubernetes 等用它存集群元数据和配置。Raft 复制的是 etcd 的 WAL / KV 日志，不是业务容器的数据 |
| Roblox 服务注册 | D1、D3、D5 反复引用的故障写报告 | 大约五台机器上的注册信息。外面是 18,000 台服务器、170,000 容器。故障写报告里还有持久存储和大约 19.8 秒的快照时间。他让你自己读，细节他标了 “I think” |
| Cloudflare | D4 三节点单向故障 | 控制面状态。半死节点把选举请求打满另外两台。pre-vote 是事后扩展 |
| Consul | 课上没讲 | 【工程实践补充】服务发现和健康检查的目录，通常 3 或 5 台 server。agent 不是 Raft 投票成员 |
| CockroachDB | 课上没讲 | 【工程实践补充】每个 range 一个 Raft 组，复制的是那一段的 MVCC 日志，不是整个数据库一个 Raft |
| TiKV / TiDB | D5 作为“别人也在写 Raft”被提到，他说不清那些实现测得怎样 | 【工程实践补充】Region 的 Raft 日志。和 Cockroach 一样，集群里有很多个小 Raft，而不是一个巨大的 |
| RethinkDB | 课上没讲 | 【工程实践补充】历史实现用 Raft 复制分片。产品已停，只说明“数据库日志”是常见用途 |

为什么是 3 或 5，不是几十：

【课程内容】他看到的部署就是这个尺寸，并感到惊讶。五台已经比把几百个地址交给客户端好 (D1 1_part009)。

【从课程推导】+【工程实践补充】：

- 每条命令都要多数派往返。成员越多，心跳和选举的消息是 O(n)，最慢的那台决定提交延迟。
- 能容忍的失败是 `(n-1)/2`。从 3 到 5，多容忍一台，延迟和运维成本已经明显上去。再到 7，多数派要 4 台同时确认，收益通常不如把数据分成多个小 Raft 组。
- 成员变更本身危险。小集群少做变更。
- 所以大系统的做法是很多个 3 副本 Raft 组，上面再分片。分片不是 Raft。Raft 只保证一组里的日志相同。

etcd 演示还说明客户端库必须知道全部投票成员。这和“只连一个负载均衡地址”不是同一个设计。生产客户端会做 leader 发现，但发现信息本身不能靠一个会单点的注册中心，除非那个注册中心也有自己的容错故事。

## Raft 不负责什么

【课程内容】他明确划出去的：

- 应用自己的并发语义。三个客户端的写，到达顺序就是日志顺序。Raft 不选一个“更合理”的顺序 (D4 2_part039–2_part040)。
- 客户端去重。§8 的序列号属于应用 (D4 2_part041)。
- 把执行结果送回某一个等待的 socket。他试了 future、回调、UUID，称为噩梦，Raft 核心不关心你用哪个 (D4 2_part036)。
- 半死节点和拜占庭。模型是全活或全死 (D4 1_part033–1_part034)。
- 快照。本周不做 (D3，D5)。
- 成员变更。第 6 节超出他当时的把握 (D5 2_part039)。
- 持久化到耐掉电介质。知道必须做，不知道写在哪一层 (D5 2_part038)。

【课程内容】只读的领导权证明他描述了，没实现。所以“线性读的全部细节”不在这门课的代码里。

【工程实践补充】Raft 本身还不负责：

- 分片和再均衡。那是多个 Raft 组之上的调度。
- 分布式事务。事务管理器可以用 Raft 复制自己的日志，Raft 不提供两阶段提交。
- 线性化读的全部工程：lease、ReadIndex、follower read。§8 的等待区是其中一种，不是唯一实现。
- 多 Raft 组之间的时钟和成员视图。
- 客户端如何跨 leader 变更重试而不破坏幂等。序列号是最低要求，会话和租约是额外的。
- 磁盘满、快照失败、成员变更和快照同时发生。这些是实现事故的高发区，论文只给协议轮廓。

若你的系统需要这些，Raft 是控制面或分片日志的内核，不是整个分布式系统。他第一天的 Roblox 图就是这个意思：外面成千上万台机器，Raft 只在中间那五台上。
