# 09 — 故障时到底发生什么

这一章把课上出现过的故障收成可以顺着时间读的剧本。每个剧本标了它证明的机制。没有在录音里做完的，写明是白板还是演示。

## 1. Problem

快乐路径是：leader 追加，多数回复，提交，执行，答复。课程的价值在快乐路径失败的方式。他第一天就说，除了死机，还有没死但不能通信；后面还有半死、重试、迟到的 RPC、客户端不放弃。

## 2. Naive Solution

- 崩溃 = 分区 = 超时 = 同一种“失败处理函数”。
- Leader 一死，所有在途命令都算失败，客户端必须换一个结果。
- 旧 leader 一旦被分区，就会立刻知道并下台。
- 客户端重试是 Raft 的事。
- 只读随便问一台。

这些都会在下面某个剧本里破掉。

## 3. Why It Fails

见各剧本。这里只记一条总原则，来自 D4/D5：

- 没提交的可以消失，客户端本来就不该听过它。
- 提交了的不能消失。若消失，要么实现错了，要么你用多数派提交了旧 term（Figure 8）。
- 旧 leader 可以继续自以为是。安全来自它提交不了，不是来自它的自我认知。

## 4. Raft Solution

每个剧本末尾写它依赖的机制。总依赖是：term、多数派交集、选举限制、只提交当前 term、日志冲突时只删未提交后缀。

## 5. Example

### Leader 在复制前崩溃

【课程内容】逻辑来自“未提交可以吹掉”，不是一场单独的 kill demo。

```text
时间 →

A Leader:  append X 到本地日志
A:         崩溃，AppendEntries 还没出去

B/C:       超时，选出 B
B 的日志没有 X

X 消失。客户端若还在等，超时。
客户端可以安全重试，因为没有人执行过 X。
```

依赖：没到多数派就不提交；新 leader 不必有未提交条目。

### 复制到一台，没有多数

五台，他的数字习惯 (D5 1_part003–1_part004，D2 的两台侧)：

```text
A leader
A 和 B 有 X
C D E 没有
多数是 3。X 未提交。客户端没被通知。

A 崩溃
C/D/E 一侧可以选出没有 X 的 leader
新 leader 写入自己的条目，覆盖 X 所在的 index

这是允许的。
```

若集群只有 3 台，A 和 B 有 X 就是多数。那就不是这个剧本，X 应该已经可以提交（还要看 term 规则）。不要把“复制到一台”在 3 台和 5 台里当成同一件事。

### 已经提交，回复客户端之前崩溃

```text
Client → A: SET x=10
A 复制到 A+B，commit，apply
A 在 send(response) 之前崩溃

Client 超时
B 成为 leader，日志里仍有 SET x=10
状态机最终会有 x=10

Client 重试 SET x=10
新 leader 再追加一条 SET x=10
两台都会执行两次
```

【课程内容】D4 2_part040–2_part041 的分区版更曲折，结果一样：命令已经在新 leader 的日志里，客户端还连着旧 leader，超时后换一台再提交，日志里两份。论文 §8：客户端给每条命令一个序列号，应用记住每个客户端处理过的最大序号。Raft 不管。

他 D5 用 UUID 解决的是“回复找到等待者”，不是这个去重。两套 id 可以是同一个，但用途要分开：

| id | 用途 |
| --- | --- |
| 事务 UUID | 把 apply 结果送回这次 RPC 的等待者 |
| 客户端序列号 | 同一个逻辑命令重试时不要执行两次 |

### 网络分区：A | B C

【课程内容】D2 白板 + D5 GET 白板 + D1 etcd。合成一条时间线。

```text
时间 →

A Leader(T1) ---- 写入 X ---- 分区开始 ----------------
                              \
B Follower ------------------- timeout → Candidate(T2) → Leader(T2)
                              /
C Follower ------------------- vote B ------------------------

A 仍认为自己是 Leader(T1)
A 可以本地 append Y
A 的 AppendEntries 到不了 B/C
A 得不到多数，不能 commit Y，不能对客户端说成功

B 成为 Leader(T2)
B 能接触 C，2/3 多数
B 可以 commit 自己 term 的新条目

分区恢复

A 收到 B 的 term=2 消息
A: currentTerm=2，变 Follower
若 A 的未提交尾巴和 B 冲突，A 删除尾巴，接上 B 的日志
```

A 在分区期间对客户端的写会超时或一直 pending。这不是安全失败，是可用性失败。etcd 在只剩一台时 GET 超时，是同一类：少数派不服务 (D1 1_part008，D5 2_part037)。

### 分区两侧都有客户端在写

D5 2_part036，为了说明 GET：

```text
C1 在多数派形成之前或当时:
  set x=13 被复制，甚至可能已经在整个集群提交

然后切开

旧 leader 侧: 仍显示 x=13，而且它不知道自己过期
新 leader 侧: set x=42 提交成功，那边的已提交值变成 42

若两边都回答 GET:
  一边 13，一边 42
```

学生说：只返回已提交的不就安全了？他同意“必须已提交”，然后说这不够。旧 leader 的已提交是旧世界。你必须问到**现在仍能联系到多数派的那个 leader**。

论文 §8 的做法，他称为很麻烦，没实现 (D5 2_part036)：

```text
GET 不进日志（它不改变状态）
放进等待区
leader 本来就在发 AppendEntries，空的也算
若这一轮得到多数 follower 的响应
说明我现在还是 leader
这时才执行等待中的 GET
```

学生以为没有新事务就没有 AppendEntries。心跳就是 AppendEntries。学生说大概一秒内会发现自己没有多数；那一秒是学生的数，不是他的常数。

D1 etcd：三台只活一台时 GET 坐到超时。他说 D5 那就是这件事 (D5 2_part037)。

### Split vote

```text
A 投 A
B 投 B
C 投 A
D 投 B

没有多数
本 term 作废
随机超时，某处先醒，term+1，再试
```

D1 visualizer：两个接近的超时都变成 candidate，消息暴增，最后有一个赢了。他没展示永不结束的分裂。规则上你要能再开一轮 (D1 2_part003，D5 1_part004–1_part005)。

两台机器的 demo：它们可以轮流当 candidate，谁也赢不了。第三台进来才有多数 (D5 1_part039)。

### Stale leader

```text
旧 leader term=3 从分区回来
新 leader term=5 已经在提交

旧 leader 的 AppendEntries(term=3) 被拒绝
响应里 term=5
旧 leader 看见 5 > 3，step down
```

它必须下来，否则它会继续给还听得见它的少数节点提供一个假的写入点。就算它不下来，它也提交不了新条目——安全的底线在多数派，不在它的自我认知。下来是为了让它停止干扰，并让它最终接上新日志。

D5 1_part001：旧消息不要执行。回复里带上自己的 term，让对方把自己修好。学生担心对方会只把 index 减一再试。减一再试停不下来，除非回复里的更高 term 被处理。

### 三台里死两台，或五台里死三台

```text
Visualizer (D3 1_part039):
  已死两台，再杀掉 leader，五台剩两台
  S1 一直 RequestVote，失败，再试
  两台活着的在打架
  没有 leader
  他把这叫做你不想要的：整个集群死了

重启一台，凑够 3，选举能完成
新 leader 没有死人的 nextIndex 表
它从 7 往回退，去接只有 2 条日志的机器
```

可用性要求多数派活着。这不是实现可以“优化”掉的。

### 半死：Cloudflare

【课程内容】D4 1_part033–1_part034。三节点，一台能把包送出去，回不来。它听不到 leader，于是不停选举。投票请求打到另外两台健康节点上，像拒绝服务。那两台本来能工作。

论文假设服务器要么全活要么全死。TLA 规格没有“半死” (D5 2_part005)。所以“Raft 被验证过”挡不住这次故障：故障走出了假设。

扩展叫 pre-vote：真的变成 candidate 之前先问一轮，听不到回应就不能开始选举，从而不抬高 term、不喷投票。不在论文里，课上不要求写。

他因此希望自己的进程也全活或全死。一个 Python 线程异常退出，其他线程还在，他曾经对着“为什么死锁”调很久，其实是有一部分已经死了。他的核选项是捕获异常后 `os._exit` (D4 1_part032–1_part033)。Rust 学生用 `unwrap` 把线程打崩，是同一类 (D5 1_part040)。

### 杀掉对端之后的 socket

【课程内容】D5 1_part040。Leader 继续复制，对已死 follower：connection refused，或 broken pipe。他平时把这些打印关掉，因为机器不在时会刷屏。正确处理是丢掉这次发送，等下一轮。`unwrap` 会把 panic 传遍线程，应用状态直接坏掉。

### 洪水

【课程内容】D5 1_part041。控制台命令 `flood`，大约 100,000 次尽快 `submit`。他预期死锁、崩溃、竞态或 Raft 出错。当天实际死在解析：`invalid literal`，以及他怀疑 `send` 不是线程安全的——控制台在状态机外面。实验没完成。教训是：并发入口不止 RPC 处理函数。

### 他的 fuzzer 留下的 bug

【课程内容】D5 2_part034。随机投递消息，已提交条目不得变化的断言响了。不是 Figure 8，因为 term 检查已经按论文加回去了。他决定把 bug 留在代码里，因为“测试把 bug 暴露出来”这件事本身值得想。不要把课程结束时的实现当成正确的 Raft。

## 6. Invariant

这些剧本共同维持：

- 少数派不能提交。
- 旧 term 不能提交“看起来已经在多数派上”的旧条目。
- 未通知客户端的条目可以消失。
- 通知过的不能消失。通知的定义是 leader 在提交并执行之后发出了答复；答复丢失时，客户端的重试必须由应用去重，否则“不能消失”仍成立，但“只执行一次”不成立。
- 更高 term 最终会把旧 leader 变成 follower，只要双方还能交换一条消息。
- 半死不在不变量里。撞上它，不变量可以全部为真，系统仍然被选举风暴打满。

## 7. Failure Cases

上面就是失败案例。再补一个容易漏的组合：

**提交成功、分区、客户端重试、同时 GET。**

```text
x=13 已提交
分区
新 leader 提交 x=42
旧 leader 对 GET 若直接返回 13，违反人们以为自己在读“现在”
新 leader 对重试的 set x=13 若没有序列号，会把 13 再写一次，盖掉 42
```

两件事都不是 Figure 2 的复制循环能单独解决的。一个要读路径证明领导权，一个要应用层去重。

## 8. Implementation Notes

调试这些剧本时，他实际用过的工具：

- Visualizer：停服务器、看 nextIndex、看 commitIndex 在死人时仍前进。
- 假网络：丢消息、以后还要重复和乱序 (D5 2_part008–2_part009)。
- 控制台：`update` 手动心跳，`show log`，`set x 42`。控制台自己会崩。
- 三节点真网络：先两台看选举失败，再加第三台。
- 杀进程看 socket 错误，而不是假设 TCP 会给你一个干净的“节点已死”事件。

不要一开始就随机丢包。先让 Figure 7 的两份日志收敛，再让五台在有计时器时收敛，然后再丢 (D4 1_part003–1_part004)。

## 9. Common Bugs

- 分区愈合后旧 leader 不看响应里的 term，继续当 leader。
- 把“复制到的机器数 ≥ 1”写成提交。
- 3 台和 5 台共用一个“至少一台 follower 成功”的判断。
- 客户端超时就在本地显示失败，但命令其实已提交。用户再点一次，出现两次转账。这是应用 bug，他明确不让 Raft 核心背锅。
- GET 读 leader 内存里的最后一条，而不是已提交前缀。
- 杀死 follower 后发送路径 panic，leader 自己退出。
- 用 `os._exit` 之前不打印致命错误，进程消失，你不知道是哪一个线程。

## 10. Course Insight

旧 leader 继续相信自己，是正常状态，不是例外。Raft 的安全不要求所有人的信仰一致，只要求能提交的那一边只有一边，并且它提交的东西未来的 leader 也有。

他把 Cloudflare 放进来，是为了划边界：模型外面的故障，算法可以“正确”地打满集群。全活或全死既是论文假设，也是他想让你的进程遵守的调试纪律。
