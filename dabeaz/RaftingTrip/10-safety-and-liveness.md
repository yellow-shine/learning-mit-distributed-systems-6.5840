# 10 — Safety、Liveness，以及 Raft 没有破解 FLP

## 1. Problem

两件不同的事经常被说成“Raft 保证正确”：

```text
Safety:    永远不错
Liveness:  最终会往前走
```

错，指的是两个状态机在同一个 index 执行了不同命令，或者客户端被告知成功的命令后来消失。往前走，指的是有新 leader、新命令能提交。

可以永远不错、同时永远不往前走：网络一直断开，没有多数派。也可以看起来在往前走、其实在错：Figure 8 那种错误提交。

## 2. Naive Solution

- 有 leader 就有安全。
- 多数复制就有安全。
- 超时设得够短就既安全又活。
- TLA+ 通过了，所以实现是对的，所以 Cloudflare 那种事故不该发生。
- 随机选举“解决了”不可能定理。

## 3. Why It Fails

有 leader 不够。分区两侧可以各有一个 leader，term 不同。安全依赖旧的那个提交不了。

多数复制不够。Figure 8 的条目可以在某一时刻位于多数机器上，仍会被下一任覆盖。缺的是“这条是当前 term” (D5 2_part000–2_part003)。

超时不提供安全。超时只影响谁先醒来。安全来自投票和提交规则。把超时调得很短，只会增加 split vote，不会让日志更正确。

TLA 通过证明的是规格在其假设下的性质。半死节点不在假设里，验证不会替你挡下选举风暴 (D5 2_part005)。规格也不是 Python。转换成实现时可以写错任何一行 (D5 2_part006)。

## 4. Raft Solution

【课程内容】他没有用下面这些英文名字开讲。他讲了组成这些性质的机制。名字是【Raft 论文补充】，方便对论文 §5.4 和面试。

### Election Safety

一个 term 最多一个 leader。

依赖：

- 每个服务器每个 term 最多投一票 (`votedFor`)。
- 当选需要多数票。
- 两个多数派相交，所以不可能有两个候选人在同一 term 都拿到多数。

课上的对应句：不能在同一次选举投两次；3/5 或 2/3 才赢 (D5 1_part003)。

### Leader Append-Only

Leader 不覆盖、不删除自己的日志。新命令只追加。

依赖：删除后缀的代码只出现在 follower 的 AppendEntries 处理里。Leader 的 `append_new_command` 总是成功，不走冲突删除 (D3 1_part001)。

他没有把这条起名。他的操作是：leader 侧那个函数永远能写。

### Log Matching

若两份日志在某 index 上的 term 相同，则该条命令相同，且前面的前缀相同。

依赖：

- Leader 在一个 index 上只创建一条，且不改。
- Follower 写入前检查 `prevLogIndex` + `prevLogTerm`。
- 冲突才删除后缀；相同 term 则保留。

这是 `(index, term)` 能当指纹的原因。见 [07](07-log-consistency.md)。

### Leader Completeness

若一条日志在某个 term 被提交，则它出现在所有更高 term 的 leader 日志里。

依赖，缺一不可：

1. 提交时它在一个多数派上，并且是提交者当前 term 的条目。旧 term 的“多数”不算提交。
2. 任意选举多数派和那个提交多数派相交。
3. 相交的那台投票者有这条已提交日志。up-to-date 规则让它拒绝一个没有这条的候选人。
4. 因此候选人没有这条就得不到多数票。

他的口语版：没有已提交条目就不可能赢 (D5 1_part004)。Figure 8 说明为什么第 1 点不能省。省了的话，“在多数派上”可以是一个未来 leader 没有的条目。

### State Machine Safety

若某台在某个 index 已经应用了一条命令，则没有任何服务器会在该 index 应用另一条命令。

依赖：

- 只应用 `lastApplied+1 .. commitIndex`。
- 已提交前缀不会被改写（Leader Completeness + leader 不删自己的日志 + follower 只在冲突时删未提交后缀）。
- apply 不跳号、不并发地执行同一个 index。

课上的对应物：已提交就是冻结；assert 最后一条已提交条目不得变化；命令 4 不能跑在命令 3 前面 (D4 2_part000，2_part005，D5 1_part030–1_part031)。

他没有证明这些箭头。证明在论文 §5.4。读的时候把 Figure 2 当规范，不要当摘要。他的课程方法是用失败剧本理解每一条 if，而不是背性质名字。

## 5. Example

三节点，把五条性质放在一个分区里看。

```text
A Leader(T1) 提交了 index 1 = SET x=1
  Election Safety: T1 只有 A
  该条在 A+B 上，term 是 1，等于当时的 currentTerm

分区 A | B C

B Leader(T2) 
  不能当选成功除非它的日志至少和 C 一样新
  若 B 和 C 都有 index 1，B 当选后仍有 SET x=1
  Leader Completeness 保住 x=1

A 在 T1 继续写 index 2
  只有 A，不能提交
  B 后来发来的 T2 日志若在 index 2 冲突，A 作为 follower 删掉 index 2
  A 不能删 index 1，因为 prev 匹配且 term 相同

两边都不会在 index 1 apply 出不同命令
State Machine Safety

在分区期间没有新的全局提交
Liveness 暂停，Safety 仍在
```

## 6. Invariant

上面五条就是安全不变量。实现里他真的写过的是更局部的：

- term 不减
- commitIndex 不减
- 已提交条目对象不变

局部 assert 失败 ⇒ 安全已经破了。局部 assert 通过 ⇒ 什么都证明不了。Figure 8 可以很久不出现 (D5 2_part008)。

## 7. Failure Cases

**无限分区。** 没有多数派。Safety 仍在：没有人能提交新的冲突历史。Liveness 没有。Raft 不能凭空保证进展。

**所有超时完全相同，且网络让它们永远同时醒。** 理论上可以一直 split vote。论文和课程都用随机超时把这变成实际中会结束的事，不是逻辑上的必然。他说随机性是让它工作的最重要因素 (D5 1_part005)。这是活性，不是安全。

**时钟任意快慢，但没有“最终会有一段安静时间”。** 选举可能永远完不成。这就是下一节。

**实现漏了 term 检查。** Safety 在一个特定崩溃序列上失败。活性看起来很好，因为错误提交也算“往前走了”。

## 8. Implementation Notes

不要在业务代码里 `assert` 五条性质的全文。它们是全局的，单机看不全。他的做法是单机能看的单调性和“已提交条目没被覆盖”。集群测试则是：跑完之后日志相等，Figure 6 里该赢的赢。

【MIT 6.5840 实现补充】tester 的失败模式经常是活性：选举超时和心跳的比例不对，或者在错误的锁里发 RPC，导致计时器不能触发。Safety 失败更安静：两个节点 apply 了不同命令，tester 过一会儿才对比日志。Beazley 的“先让日志相等”是同一类 oracle。

## 9. Common Bugs

- 用活性测试代替安全测试。集群能选出 leader，不代表不会丢已提交条目。
- 关掉 Figure 8 的 if，演示仍然全绿。
- 两个 candidate 用锁“保证只有一个 leader”，从而在同一 term 外又发明一个 leader。Term 已经是那个锁。再加一个会在分区时卡死。
- 为了“更快恢复”允许少数派提交。

## 10. Course Insight

Safety 是“通知过客户端的历史不会被改写”。Liveness 是“如果多数派能互相通话，而且这种通话能持续比选举超时更长的一会儿，就会有人当选并复制日志”。

他把随机性说成最重要的东西时，谈的是第二句。第一句里没有随机数。

## FLP：课上没讲，这里只放边界

【Raft 论文补充】【理论补充，课程未涉及这个名字】

FLP（Fischer, Lynch, Paterson, 1985）说的是：在异步网络里，进程只会崩溃、不会拜占庭，只要允许哪怕一条消息无限延迟，就没有确定性共识算法能同时保证：

- 安全：永不决出两个不同的值
- 活性：所有正确进程最终一定决出值
- 并且对所有时间交错都成立

异步的意思是没有上界：你不能用“等了 150ms 一定是它死了”作为逻辑前提，因为那条消息可能只是慢。

Raft 没有破解 FLP。它放弃的是“对所有时间交错都保证活性”。

它换成工程假设：

```text
超时          把“沉默”当成故障的启发式
随机选举      让同时醒来的概率变小，失败了就换 term 再试
最终的稳定    存在一段比选举超时更长的时间，
              多数派之间的消息能按时到达
```

在这段稳定期里，最多一个 candidate 先超时，拿到多数票，心跳把其他人按住，复制可以完成。若这段稳定期永远不来，Raft 可以一直选下去，同时不破坏安全。

这就是“Raft 依赖实际系统里的时间假设来获得 liveness”。安全仍然不依赖时钟准确，只依赖：多数派交集、日志比较、term 单调。时钟错了，最坏是不稳定，不是提交两条矛盾历史——前提是你没有用墙钟去比较日志新旧。比较日志只用 index 和 term。

他课程里最接近这段话的材料是：随机超时、两台永远选不出、分区时少数派不服务、以及“状态空间大到人脑覆盖不了”(D5 2_part000)。不要把 FLP 三个字母写成他的课堂内容。
